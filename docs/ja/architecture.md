# 仕組み

[English](../architecture.md) | **日本語**

Worktabs は Electron のアプリです。worktree ごとに code-server を起動してタブに出し、Claude Code の hooks と Codex の app-server のイベントで会話の状態を受け取ります。設計の根拠になった調査と検証は [research.md](../research.md)（英語）にあります。

## リポジトリの読み直し

`src/commands.js` は、ローカルと WSL で共通のコマンドのアダプターを持ちます。クローン・タスク・GitHub・エージェントの CLI のコードは、これを直接使います。標準入力、cwd、明示した環境変数の上書き、タイムアウト、失敗したときの出力、Windows でプロセスを隠すことは、そのまま保ちます。WSL のコマンドは、ディストリのシェルの環境と Linux のパスのままです。`src/repos/worktrees.js` は、互換のための export を残しつつ、リポジトリの検出と Git の worktree の操作を、アダプターとは分けておきます。

`src/repos/github.js` は、アプリで共通の GitHub のクライアントの API を持ちます。`src/repos/github-client.js` は、注入したコマンドと Git の読み取りでクライアントを作ります。クライアントはそれぞれ、設定したホスト、SSH のホスト名の引き当て、サインインしているホストのキャッシュを持ちます。GraphQL の呼び出しは、コマンドの組み立てと JSON の扱いを共有します。ブランチの PR を読むときは、成功した応答が要ります。公開範囲と Approve 済みの PR を読むときは、失敗した GraphQL の応答の一部のデータも使えます。

リポジトリの検出と GitHub の情報は、`src/repos/repository-service.js` がまとめて扱います。`repos.json` のスナップショットと、番号を付けたサイドバーへのメッセージを持ちます。一覧の読み込みの依頼はまとめます。読んでいる間に明示の読み直しや追加があると、もう 1 回読みます。クローンで足したものはすぐに出て、それより古い一覧の結果でも消えません。失敗した取得元は前の分を残し、成功して空だった取得元は消します。一覧から外れたものは、キャッシュしたリモートと、まだ読み直していない worktree の一覧を失います。

公開範囲の読み込みは 1 つずつ動かし、その間に依頼があれば、あとでもう 1 回だけ読みます。自分のリポジトリの結果は、リモートと、名前を変えたリポジトリの今の URL に照らしてから出します。失敗した GitHub のホストは、最後の結果を残します。Approve 済みの PR の読み直しは、後から来た依頼をまとめるので、明示した `all` の読み込みが消えることはありません。定期的な読み込みは、動いている WSL のディストリにだけ聞き、眠っているディストリの印は残します。明示した一覧の読み込みと `all` の読み込みは、WSL を起動することがあります。メニュー（`src/window/menus.js`）・クローンのダイアログ・IPC（`src/window/ipc-table.js`）はこのサービスを呼び、Electron に関わる部分は `main.js` に残します。

## タブのライフサイクル

`src/conversations/conversation-opening.js` は、行のクリック、補助拡張の登録、待っている移動の期限、最初の会話の送り出し、復元の警告をまとめて扱います。タブとサーバーの起動の識別を読む関数、補助拡張の呼び出し、タイマーを受け取ります。タブの切り替えと後片付けで、待っている前出しを取り消すのは、タブのライフサイクルからこのモジュールに任せます。フレームでの実行とネイティブのダイアログは、Electron のアダプターに残します。画面に出ている Codex のスレッドの確認と、最初のタスクの下書きの扱いは、今までのモジュールのままです。

`src/repos/worktree-removal.js` は、削除の前の確かめ、確認のダイアログの持ち主、タブを閉じること、worktree とブランチの削除、保存領域の片付けをまとめて扱います。Git を読む関数、会話とタブの状態、ダイアログ、ネイティブの操作を受け取ります。削除を止める条件と、読めなかったときの今までの扱いは、そのままです。削除の前に primary を開きます。削除に失敗したら、その worktree のために残している保存領域はそのままにし、成功したら、ブランチを消す（選んだとき）前に消します。ブランチを戻すための通知は、Electron のアダプターに残します。

`src/tabs/tab-lifecycle.js` は、開いているタブの識別、その順番、アクティブなタブ、サーバーの起動と停止の移り変わりを持ちます。`src/main.js` は、Electron の view、サーバーのマネージャー、危険を知らせるダイアログ（`src/tabs/tab-risks.js`）、設定の共有、ファイルとクッキーの保存（`src/tabs/tab-store.js` が tabs.json を持ちます）を渡します。ライフサイクルは Electron なしでテストできます。

- タブを閉じると、待っている起動は無効になります。古いタブの Git の読み取り、サーバーの準備、進み具合、クッキーの書き込みの完了が、同じフォルダで開き直したタブを書き換えることはありません。
- 同じタブ ID の起動は、前の起動が終わってサーバーを手放すのを待ちます。古い起動が、入れ替わったサーバーを止めることはありません。マネージャーは終了のイベントに起動の持ち主を付けて返すので、古い終了で、入れ替わったものが止まったことにはなりません。
- 閉じる・休止・再起動・起動の失敗・サーバーの終了では、1 つのアダプターを通して、エージェントと補助拡張の実行時の状態を消します。開いているタブが止まっても Codex の履歴は残り、閉じると消えます。タブの前出しのタイマーは、開いているタブの表から外れたあとでも消します。
- 確認とチャット欄の幅の読み取りは、そのときのタブとサーバーの起動のものです。アプリが待っている間にどちらかが変わると、その操作は入れ替わったものには効きません。グループを閉じるときは、次のアクティブなタブを 1 回だけ選び、途中でそのグループのほかのタブを起動することはありません。
- ライフサイクルは、`tabs.json` のタブの部分を作って戻します。覚えているポートには `src/tabs/tab-ports.js` を使います。リポジトリを使った時刻とチャット欄の幅は、メインプロセスが同じファイルに持ちます。戻した裏のタブは休止したままで、起動するのはアクティブなタブだけです。プロバイダーと Codex の履歴の情報は、アクティブなタブが起動する前に戻します。
- 保存したタブは、サイドバーが新しいタブを保存できるようになる前に戻します。`src/tabs/startup-gate.js` は、code-server、プロセスのラッパー、必要な拡張、言語パックの用意ができるまで、すべてのタブの起動を止めておきます。ライフサイクルがマネージャーを選ぶのは、この共通の待ちのあとです。待っているタブを閉じたり再起動したりすると、自分の起動だけを取り消し、ほかのタブのための準備は取り消しません。起動の失敗は、待っているタブとあとから来たタブにエラーとして届き、入れ終わっていない状態でサーバーを起動することはありません。

## code-server

拡張の選択とインポートの段取りは、`src/code-server/extension-management.js` にあります。候補のキー、互換性の確認、前の版の用意（ステージング）、インポートと元に戻す依頼、インポートが成功したあとのギャラリー（Open VSX）の確認を持ちます。拡張の検出、サーバーの操作、版の読み取り、予定の組み立て、更新の状態は注入します。ネイティブのファイルの選択と、デスクトップの VS Code を開くことは `src/window/settings-actions.js` にあり、ネイティブのファイルを選ぶ画面を `main.js` から受け取ります。ステージングのエラーは更新のトランザクションが始まる前に起きるので、動いているタブを止めたり、入っている拡張を置き換えたりしません。

更新のトランザクションは、準備、作業中のタブがなくなるのを待つこと、取り消し、タブを止めて再開する共通の境目に、`src/code-server/update-coordinator.js` を使います。切り替えの間に依頼された起動は、切り替えが終わるまで待ちます。成功しても失敗しても、止めたタブのうち残っているものはすべて再開します。取り消した古いトランザクションが、新しいトランザクションに進み具合を出すことはありません。作業中かを確かめている間にタブが起動すると、切り替えはしません。Codex の拡張が動いているのにターンを見られないタブは、今までどおり更新を止めます。

ギャラリーからのインストールと元に戻すことは、`src/code-server/update-strategies.js` にあります。code-server の新しい設定は、ローカルで試しに起動して確かめたあとでだけ確定し、前のリリースは手で戻すために残します。WSL での失敗は別に知らせます。インポートしたスナップショットには、`src/code-server/extension-imports.js` の `applyImportBatch` を使います。Linux 向けのインポートは、今までどおり、対応するディストリが次に起動したときに入ります。使っていなかった、再起動をあとに回すタイマーは取り除きました。今の流れでは、入れる前に作業していないタブを止め、トランザクションのあとで再開します。

worktree ごとに 1 プロセス起動します（`127.0.0.1` のみで待ち受け）。

- `user-data-dir` は worktree ごとに分け、拡張フォルダは共有します。VS Code の設定は、同じリポジトリの worktree のタブで共有します（[下](#vs-code-の設定の共有)）。
- 認証には `--auth password` を使います。起動のたびにランダムな値を `HASHED_PASSWORD` に渡し、同じ値をアプリがタブのクッキーに直接書き込みます。このクッキーがないとアクセスできません。平文のパスワードは存在しないので、ログイン画面から入ることもできません。
  - code-server は起動後に `HASHED_PASSWORD` を自分の環境変数から消すので、拡張や claude には渡りません。
  - クッキーはポートで分かれないので、`--cookie-suffix` でインスタンスごとに名前を変えています。
- VS Code 内蔵の AI 機能（Copilot のチャット）は既定で切っています（`chat.disableAIFeatures`）。インスタンスごとに起動していた agentHost と copilot-runtime がなくなり、メモリが約 3 割減ります。右のサイドバーに VS Code が出す組み込みのチャットは空になるので、アプリが Claude Code のチャット欄に替えます（[下](#補助拡張)）。
- VS Code の配色は OS のライト／ダークに合わせます（`window.autoDetectColorScheme`）。
- この 2 つはインスタンスの既定値なので、VS Code の設定から変えられます。
- 表示言語は、いつも `--locale` で渡します。渡さないと、code-server はブラウザの言語に従い、拡張フォルダにある言語パックで表示するためです。設定の `locale` か、それが空ならアプリの UI の言語で、その言語パックを入れる拡張に加えます（`src/i18n/index.js` の `displayLocale` と `withLanguagePack`）。code-server が翻訳に使う言語パックの一覧（`languagepacks.json`）は、VS Code の中から拡張を入れたときにしか作られません。アプリはコマンドラインで拡張を入れるので、起動のたびにこのファイルをインスタンスごとに書きます。
- ポートは worktree ごとに固定して `tabs.json` に保存します。VS Code Web は、画面の状態（開いているファイル、エディタのタブの Claude の会話、サイドバーのビュー、パネルの大きさ）をオリジン（ポート）単位でブラウザに保存するので、ポートが変わると前の画面に戻れません（`src/tabs/tab-ports.js`）。
  - タブを閉じても、ポートを覚えておきます。開き直すと同じポートで起動するので、閉じる前の画面に戻ります。
  - 覚えているポートは、ほかのタブに使いません。同じオリジンになると、VS Code がフォルダによらず持つ状態（global）が、2 つのタブで混ざるためです。新しいポートを取るときに、OS が覚えているポートを出したら、取り直します。更新の確認で起動する code-server も同じです。
  - 覚えているポートをほかのプログラムが使っていたら、新しいポートで起動します。画面は空から始まり、前のポートは忘れます。
  - ポートを忘れるのは、アプリから worktree を削除したとき、起動したときにフォルダがなくなっていたとき（アプリの外で削除したとき。WSL のフォルダは見ません）、閉じたタブが 200 を超えたとき（最後に使ったのが古いものから）です。
  - 忘れたポートのオリジンの保存領域（IndexedDB など）は消します。あとでそのポートを取ったタブが、前の画面を引き継がないようにするためです。クッキーは消しません。クッキーはポートで分かれないので、ほかのタブのクッキーまで消えてしまいます。
- Windows 版 code-server の既定リダイレクト（`?folder=C:\...`）は開けないので、`?folder=/c:/...` 形式の URL をアプリが組み立てます。
- 起動前に、`CLAUDECODE`、`CLAUDE_CODE_*`、`VSCODE_*`、`ELECTRON_*`、`CODE_SERVER_*` などの環境変数を取り除きます。
- `localhost` のポートへのリンクは、書いてあるとおりに開きます。開発サーバーがターミナルに出す URL や、ポートでサーバーが起動したときに VS Code が出す通知の「ブラウザーで開く」です。
  - VS Code は、ブラウザがサーバーと別のマシンにあるかもしれないと考えて、こうしたリンクをブラウザから届くアドレスに変えます（`resolveExternalUri`）。code-server は、これを自分のプロキシで行います（`http://127.0.0.1:<code-server のポート>/proxy/<ポート>/<パス>`）。これには code-server のログインが要りますが、既定のブラウザはログインしていません。また、パスの先頭を取り除くので、絶対パスで読み込むアプリが壊れます。
  - アプリは、こうしたリンクを `http://localhost:<ポート>/<パス>` に戻してから、ブラウザで開きます（`src/code-server/code-server.js` の `unproxiedUrl`）。変えるのは、そのタブの code-server のプロキシへのリンクだけです。WSL の開発サーバーには、アプリがそこの code-server に届くのと同じく、WSL の localhost の転送で Windows から届きます。
  - 代わりに、code-server のプロキシのテンプレート（`VSCODE_PROXY_URI`）でポートそのものを指すことはできません。code-server の画面はテンプレートを URL として読みますが、`http://localhost:{{port}}` は URL ではないので、workbench が「Invalid URL」で接続に失敗します。

## code-server の起動の決まり

`src/code-server/code-server-launch.js` は、共通の引数、ランダムな値のクッキーでの認証、表示言語、管理する設定とエージェントの起動役の用意、言語パック、応答できるようになるのを待つことを持ちます。ローカルと WSL のマネージャーは、契約のテスト（contract test）のために、通信と死活の確認を注入して使います。応答できるという返事は、そのとき捉えたインスタンスがまだ今のものであるときだけ受け取ります。起動の失敗と停止では、設定の共有のハンドルを 1 回だけ手放します。遅れて来た失敗が、入れ替わったインスタンスを止めることはありません。起動中に終了したら起動は失敗とし、応答できるようになったあとの思わぬ終了には、起動の持ち主を付けます。ローカルのプロセスグループ、WSL のエージェントへの依頼、ディストリの準備、Linux 向けの拡張の選択、希望のポートでのやり直しは、それぞれのバックエンドに残します。どちらにも属さないこのモジュールは、共通のポートと URL の関数も持ちます。`code-server.js` は、それらを今までどおり export します。

## VS Code の設定の共有

同じリポジトリ（main worktree）の worktree のタブは、`user-data-dir` の `User/` にある `settings.json`・`keybindings.json`・`tasks.json`・`mcp.json`・`snippets/`・`prompts/` を共有します（`src/code-server/settings-sync.js`）。リポジトリが違うタブや、git でないフォルダのタブとは共有しません。

- `user-data-dir` をリポジトリで 1 つにはしません。同じリポジトリの code-server が、`logs/`・`coder.json`・`globalStorage/` を同時に書くことになるためです。`User/` やファイルをリンクにもしません。ジャンクションはフォルダにしか使えず、ハードリンクは保存のしかたによって切れ、シンボリックリンクは開発者モードか管理者の権限が要ります。どれも WSL のタブには使えません。
- 共有の内容は、データフォルダの `repos\<リポジトリID>\` に置きます（ID は main worktree のパスのハッシュ）。WSL のリポジトリのものも、ここに置きます。
- タブの code-server を起動する前に、共有の内容をタブの `User/` に書きます。そのため、タブを開いたときに求める main worktree を待ってから起動します。
  - `settings.json` には、共有の設定にない既定値（`chat.disableAIFeatures` など）を共有に足してから書き、アプリが管理する設定（`claudeCode.claudeProcessWrapper`・`claudeCode.initialPermissionMode`）で上書きします。
- 実行中は、タブの `User/`・`snippets/`・`prompts/` のフォルダを見張ります。変わると 0.3 秒待ってから、前に合わせたときと比べて変わったものを共有に取り込み、同じリポジトリのほかの実行中のタブに渡します。
  - code-server は、自分で書いていない `User/` の変化を読み直しません。外から `settings.json` を書き換えても、画面は変わりません（Windows の実機で確かめました。起動のときには読みます）。そこで実行中のタブには、補助拡張が VS Code の設定の API（`WorkspaceConfiguration.update`）で設定を書きます（`/settings`）。VS Code は自分で `settings.json` に書き、その場で反映します。テーマも変わり、補助拡張が知らせて、サイドバーの色も合います。
  - 補助拡張がまだ動いていないタブと、VS Code が書けなかった設定（どの拡張も登録していないキーなど）は、アプリが `settings.json` に書きます。そのタブの次の起動で反映します。
  - `settings.json` はキー単位で合わせます。消したキーも消します。2 つのタブで別々のキーを変えても、両方残ります。同じキーを変えたときは、後に変えたタブの値になります。
  - まだ取り込んでいない変更があるタブには、そのキー（ほかのファイルなら、そのファイル）を書きません。次に取り込んで、ほかのタブに広げます。
  - コメント付き（JSONC）の `settings.json` も読みます（`src/code-server/jsonc.js`）。書くときは変わったキーだけを書き換えるので、ほかの行とコメントは残ります。
  - 読めない `settings.json`（書きかけなど）のタブは、読めるようになるまで飛ばします。空のファイルや、ファイルがないときも、書いている途中とみなして何も消しません。
  - ほかのファイルは、丸ごと写します。VS Code の API では書けないので、ほかの実行中のタブには、次の起動で反映します。
  - 管理の設定は共有に入れず、実行中はほかのタブに写しません。起動のたびに、そのタブの値を書きます（Windows と WSL で、ラッパーのパスが違うため）。
  - 会話を前に出すときと、新しい worktree の最初の会話を開くときに補助拡張が一時的に書く `claudeCode.preferredLocation`（[下](#補助拡張)）も、ほかのタブに写り、すぐ元に戻ります。
- 休止・再起動・終了で止めるタブからも、最後に変わったものを取り込みます。止まっているタブには書かず、次の起動で共有の内容にします（worktree を削除するときは、フォルダも消すため）。
- 共有を初めて作るとき（移行）は、そのリポジトリの worktree（`git worktree list`）のタブの `User/` を集めます。同じキーは、更新が新しいファイルの値を使います。ほかのファイルも、更新が新しいものを使います。
- そのあとで初めて共有に加わるタブ（worktree の中のフォルダを開いたタブなど）は、共有にない設定とファイルを足し、残りは共有の内容になります。加わったタブは `repo.json` に書きます。
- worktree を削除すると、そのタブの `user-data-dir` は消しますが、共有の設定は残します。
- WSL のリポジトリのタブの `User/` は WSL の中にあるので、読み書きと見張りはエージェントが行います。
- 共有しないもの: `Machine/settings.json`（管理の設定だけ）、`workspaceStorage/`・`History/`（worktree ごとのもの）、`globalStorage/`（拡張が実行中に読み書きするファイル。実行中のタブの間で写すと、壊れるおそれがある）。拡張の有効・無効、パネルの配置、コマンドの履歴、拡張の状態（globalState）は、VS Code Web がブラウザの IndexedDB にオリジン（ポート）ごとに持っているので、タブごとです（[limitations.md](limitations.md#vs-code-の設定)）。
- `claudeCode.hideOnboarding` もタブごとで、移行にも実行中の設定の共有にも入れません。primary 以外の worktree には起動のときに `true` を書き、primary 自身の設定はそのままにします。解決した worktree のルートを、解決した main worktree と比べるので、サブフォルダのタブと、primary より先に開いたタブも同じ決まりに従います。
- primary 以外の worktree のタブでだけ、`src/agents/agent-onboarding.js` が Codex の webview を見張ります。知っている初回の案内のコンポーネントを、意味を表すメッセージ ID と props で見分け、そのコンポーネント自身の `onAccept` コールバックを呼びます。このコールバックは、案内を終えたことを拡張を通して保存し、チャットに戻ります。すでに終えた状態や、状態が遅れて届いた状態で出た初回の画面も扱います（[upstream #25146](https://github.com/openai/codex/issues/25146)）。Worktabs は、拡張の状態、認証、権限、会話、レイアウトを写しません。知らない形のコンポーネントは、拡張の元の画面のまま使えます。

## 補助拡張

[helper-extension/](../../helper-extension/) は、VS Code Web にないデスクトップ版のコマンドと、アプリから Claude の会話を前に出す仕組みを足します。`npm run build:native` で VSIX にし、起動時に共有の拡張フォルダへ入れます。

- エクスプローラーの右クリックの「エクスプローラーで表示する」。code-server は同じマシンで動いているので、Windows のエクスプローラーで開けます。補助拡張はアプリに頼み（hooks の受信口の `/explore`）、アプリが下の「エクスプローラーのタブ」の方法で開きます。アプリに届かないとき（手で起動した code-server など）は、拡張が `explorer.exe /select` で新しいウィンドウを開きます。
  - macOS では「Finder で表示する」です。表示名は `package.json` で決まるので、同じ処理のコマンドを 2 つ（`worktabs.revealInExplorer` と `worktabs.revealInFinder`）持ち、メニューの `when` の `isMac` で出し分けます。VS Code Web の `isMac` はブラウザ（アプリのウィンドウ）の OS で決まるので、WSL のタブ（Windows）はエクスプローラーのままです。
- 会話を前に出す: 補助拡張は `127.0.0.1` のランダムなポートで待ち受け、そのポートと自分のトークンを、hooks の受信口に知らせます（hooks の URL とトークンは、アプリが code-server の環境変数で渡しています）。
  - 補助拡張は、Claude Code 拡張が会話一覧（Session history）の行を開くときと同じ方法で、会話を前に出します。`claude-vscode.editor.open <session_id>` を、6 つ目の引数に `{ programmatic: 'honor-preferred-location' }` を付けて呼びます。
    - 会話がエディタのタブにあれば、拡張はそのタブを前に出します。
    - そうでなく、`claudeCode.preferredLocation` が `sidebar` なら、拡張は右のパネル（サイドバー）にその会話を出させます。右のパネルは、自分が持つ会話（前に出ている会話の背後にあるもの）の中にあればそれに切り替え、claude を新しく起動しません。なければ、履歴から開きます。
    - `preferredLocation` が `panel`（既定）だと、エディタの新しいタブで開きます。右のパネルの背後にある会話でも、2 つ目の claude で開いてしまいます。そこで補助拡張は、呼ぶ間だけユーザー設定の `preferredLocation` を `sidebar` にし、呼んだ後に元の値に戻します（設定ファイルに 2 回書き込みます）。拡張は、コマンドが呼ばれた時点の設定を読むので、これで効きます。続けて呼ばれても、1 つずつ順に行います。
    - ワークスペースの設定（`.vscode/settings.json`）が `preferredLocation` を決めているときは、リポジトリのファイルなので書き換えず、右のパネルを出すだけにします。
  - パネルの中で会話を切り替えても hooks は来ず、どの会話がどこに出ているかを、ほかの拡張から読む API もありません。行き先は拡張が決めるので、アプリはそれを知らなくて済みます。
- 新しい会話のためにチャット欄を出す: サイドバーから worktree を追加したタブでは、補助拡張がアプリに知らせてきた時点で、アプリが `/new-conversation` を呼びます。補助拡張は、チャット欄のビュー自身のフォーカスのコマンド（`claudeVSCodeSidebarSecondary.focus`）で、右のチャット欄を出して入力欄にフォーカスを移します。
  - `claude-vscode.editor.open` や `claude-vscode.sidebar.open` は、そのままでは使いません。前者はエディタのタブに会話を開き、どちらも Claude Code 拡張の `claudeCode.preferredLocation`（新しい会話を開く場所）を書き換えてしまうためです。
  - 追加のダイアログで issue・PR かやることを書いたときは、`/new-conversation` にその指示（`prompt`）を渡します。補助拡張は `claude-vscode.editor.open` を、Claude Code 拡張の「新しい会話のタブ」と同じ引数（会話、指示、列、グループ、全画面か、`{ programmatic: 'honor-preferred-location' }`）で呼びます。こう呼ぶと、拡張は `claudeCode.preferredLocation` の場所に新しい会話を開いて入力欄に指示を入れ（送信はしません）、設定は書き換えません。公開された口ではない（拡張の中の呼び方）ので、拡張の版が上がったら確かめます。
  - `preferredLocation` が `panel`（既定）だと、エディタの新しいタブで開きます。拡張は、利用者がエディタのタブで会話を開くと `panel` に書き換えるので、多くはこちらです。そこで補助拡張は、会話を前に出すときと同じように、呼ぶ間だけユーザー設定の `preferredLocation` を `sidebar` にし、呼んだ後に元の値に戻します（順番待ちも同じです）。拡張は右のチャット欄を出し（`claudeVSCodeSidebarSecondary.focus`）、そこに会話を開きます。右のサイドバーが組み込みのチャットを出していても、Claude Code のチャット欄に替わります。
  - 右のチャット欄は、初めて出たときに自分の会話を 1 つ作り、claude も起動します。指示の会話はそれとは別の新しい会話として開くので、空の会話が背後に残り、claude が 1 つ多く動きます。チャット欄を先に出してから呼んでも同じで、拡張にはこれを止める口がありません。空の会話は始めていないので、サイドバーに行は出ません（[limitations.md](limitations.md#claude-code-拡張)）。
  - ワークスペースの設定（`.vscode/settings.json`）が `preferredLocation` を決めているときは、リポジトリのファイルなので書き換えず、そのまま呼びます（その場所に開きます）。
- 右のサイドバーに Claude Code のチャット欄を出す: VS Code 1.139 は、右のサイドバー（セカンダリ サイド バー）を既定で出し（`workbench.secondarySideBar.defaultVisibility` の既定は `visibleInWorkspace`）、まず組み込みのチャット（`workbench.panel.chat`）を出します。AI の機能を切っているので（[上](#code-server)）、中身は空です。Claude Code のチャット欄は上にアイコンが出るだけで、拡張はそれが出るまでチャット欄の画面を作りません。前にチャット欄で話していた会話も戻らず、その claude も動かないので、サイドバーに会話の行が出ません。どのビューを出していたかは VS Code Web がオリジン（ポート）ごとに覚えるので、これは初めて開くタブ（新しい worktree など）と、ポートが変わったタブで起きます。
  - そこでアプリは、補助拡張が知らせてきたときに、右のサイドバーが何を出しているかをタブの画面で見ます（`src/conversations/secondary-sidebar.js`）。VS Code は、右のサイドバーで開いたビューのコンテナごとに、その id を付けた要素（`.composite`）を作り、出しているもの以外を隠します。拡張の API では、どのビューが出ているかは分かりません。
  - 組み込みのチャットが出ていれば、補助拡張の `/show-chat` を呼びます。補助拡張は、VS Code がビューごとに登録する開くコマンド（`claudeVSCodeSidebarSecondary.open`）を `{ preserveFocus: true }` で呼びます。フォーカスはエディタに残ったまま Claude Code のチャット欄に切り替わり、拡張がチャット欄の画面を作ります。前にチャット欄で話していた会話も戻ります。右のサイドバーがない VS Code では `claudeVSCodeSidebar.open` を呼びます。
  - このコマンドは、右のサイドバーを閉じていても開きます。そこで、右のサイドバーを閉じているときと、ほかのビュー（Claude Code を含む）を出しているときは何もしません。自分で閉じた右のサイドバーが、タブを開くたびに開くことはありません。
  - 補助拡張が知らせてくる（`onStartupFinished`）のは、VS Code がビューを戻した後です（開発機では、組み込みのチャットが出てから 3〜4 秒後）。それでもまだ見分けられないとき（ビューの要素がまだないとき）は、0.5 秒おきに 5 秒まで見直します。
  - サイドバーから追加した worktree のタブでは、`/new-conversation` が会話を開くので、重ねて呼びません。
  - どちらも、チャット欄を出したあとに、アプリがチャット欄の幅を決めます（[下](#右のチャット欄の幅)）。
- 設定を書く: 同じリポジトリのほかのタブで変わった設定を、アプリが `/settings` で渡します。補助拡張は、キーごとに `WorkspaceConfiguration.update`（ユーザー設定）で書き、書けなかったキーを返します（[上](#vs-code-の設定の共有)）。
- テーマの色をサイドバーとダイアログに渡す: VS Code は、テーマのすべての色を、画面の `.monaco-workbench` に CSS 変数（`--vscode-sideBar-background` など）として書き、テーマの種類（`vs`・`vs-dark`・`hc-black`・`hc-light`）をクラスで付けます。アプリはこれをタブの画面から読みます（`src/window/theme.js`）。読むのは、補助拡張がアプリに知らせてきたとき（VS Code が起動したとき）と、テーマが変わったと補助拡張が知らせてきたとき（`onDidChangeActiveColorTheme`、hooks の受信口の `/theme`）です。VS Code の拡張の API では、テーマの色の値そのものは読めないためです。

## 右のチャット欄の幅

VS Code は、新しいポートでは右のサイドバーを 300 ピクセルで出します。チャットで使うには狭いので、初めて開いたタブでは、アプリがチャット欄の幅を決めます（`src/conversations/secondary-sidebar.js`）。

- 決めるのは、組み込みのチャットを Claude Code のチャット欄に替えたとき（`/show-chat`）と、サイドバーから追加した worktree のタブで `/new-conversation` を呼んだあとです（[上](#補助拡張)）。どちらも、そのポートで初めて開いたタブです。
  - そのあとは VS Code がポートごとに幅を覚えるので、2 回目からは触りません。自分で変えた幅も、閉じた右のサイドバーも、ほかのビューを出している右のサイドバーも、そのままです。primary の幅をあとで変えても、もう開いたことのある worktree の幅は変えません。
  - 開いたあとにウィンドウの大きさを変えたときは、VS Code に任せます。
  - WSL のリポジトリも同じです。
- 幅は次のとおりです。

  | タブ | 幅 |
  | --- | --- |
  | primary 以外の worktree | 同じリポジトリの primary のチャット欄と同じ幅 |
  | primary（ポートが変わったなどで、もう一度初めてになったとき） | アプリが覚えている、その primary の幅 |
  | primary を初めて開いたとき、primary の幅が分からない worktree、git でないフォルダ | エディタ欄とチャット欄を合わせた幅の 3 分の 1（エディタ欄：チャット欄 = 2:1） |

  - エディタ欄とチャット欄を合わせた幅は、パネルを下に置いていれば、左のアクティビティバーとサイドバーを除いた幅です。
  - どの幅も、300 ピクセル（VS Code の既定）より狭くせず、エディタ欄に 400 ピクセルを残します。primary の幅を読んだときよりウィンドウが狭いと、エディタ欄が狭くなりすぎるためです。両方を満たせない狭いウィンドウでは、2:1 にします。
- 拡張の API には、サイドバーの幅を変える口がありません。そこでアプリは、エディタ欄と右のサイドバーの間の sash を、タブの画面でドラッグしたことにします。`mousedown` を sash に、`mousemove` と `mouseup` をウィンドウに送ります（VS Code 1.139 の sash は、これでドラッグを始めて追います）。VS Code は、自分でドラッグした幅と同じように、この幅を覚えます。
  - スクリプトのイベントなので、フォーカスは動きません。エディタに残ります。
  - VS Code の画面の作り（`.part.auxiliarybar`・`.part.editor`・`.monaco-sash`）と、sash が受けるイベントに頼るので、code-server の版を上げたら確かめます。
  - ほかの案はとりませんでした。`workbench.action.increaseViewWidth` は決まった量ずつしか変えられず、右のサイドバーにフォーカスを移す必要があります。VS Code が覚える幅（`workbench.auxiliaryBar.size`）を前もって書くには、ページを読み込む前に、ポートごとの IndexedDB に書く必要があります。
- primary の幅は、ピクセルで覚えます。VS Code も右のサイドバーの幅をピクセルで持ち、ウィンドウの大きさを変えても変えないためです。
  - VS Code が覚える幅はポートごとなので、primary のタブが動いていないと読めません。そこでアプリは、primary のタブを閉じるとき・休止するとき・アプリを終えるときに、タブの画面で右のサイドバー（`.part.auxiliarybar`）の幅を読み、リポジトリごとに覚えます（`tabs.json` の `chatWidths`。最後に読んだ 200 リポジトリまで）。primary を初めて開いて幅を決めたときも覚えます。
  - 新しい worktree を開くときに primary のタブが動いていれば、その場で読んだ幅を使い、覚えている幅も直します。動いていなければ、覚えている幅を使います。
  - 右のサイドバーを閉じている primary と、右のサイドバーを最大化している primary（エディタ欄が出ていない）からは読みません。前に覚えた幅のままです。
  - 読むときは、1 秒待っても答えない画面を待ちません。タブを閉じるのとアプリを終えるのを止めないためです。
- この機能より前から開いている primary で、幅を変えたことがないものは、VS Code の既定の幅のまま開きます。既定の幅かどうかを見分けて直すことはしません。その primary の幅を自分で直すまでは、そこから作った worktree も 300 ピクセルになります。

## ダイアログ

Electron の `dialog.showMessageBox` は Windows のタスクダイアログで、VS Code のテーマにも Windows のダークモードにも従わず、白く出ます（electron/electron#22231）。そこでアプリは、サイドバーとタブの上に重ねた透明な画面（`src/dialog/`）にダイアログを描きます。

- 普段は隠しておき、ダイアログを出す間だけ見せます。見えている間は、下のタブとサイドバーをクリックできず、アプリのキー（Ctrl+Alt+PageDown など）も効きません。
- `showMessageBox` と同じオプションで呼び、同じ形で答えを返します（`src/window/message-box.js`）。
- worktree の追加のダイアログも、同じ画面と同じ順番待ちに載せます（`src/dialog/add-worktree.js`）。入力中の確かめと作成は、画面からアプリに頼み、アプリは前に出ている追加のダイアログのリポジトリに対してだけ行います。
  - issue は `gh issue view --json number,title,state,url` で読みます。gh は PR の番号でも答えるので、URL が `/pull/` なら PR として、`gh pr view --json number,title,state,url,headRefName,isCrossRepository,headRepositoryOwner` で読み直します。PR の URL なら、はじめから `gh pr view` で読みます。
  - PR は、作る前に fetch します（`src/repos/worktrees.js` の `pullPlan`）。同じリポジトリのオープンな PR は `+refs/heads/<ブランチ>:refs/remotes/origin/<ブランチ>` を fetch して、それを追うブランチを作ります。フォークからの PR と、マージ済み・閉じた PR は `refs/pull/<番号>/head:refs/heads/<ブランチ名>` を fetch して、ブランチを直接作り、`branch.<ブランチ名>.remote` と `.merge` を `gh pr checkout` と同じに設定します。入力中の説明は fetch せずに出すので、すぐに出ます。
  - ブランチ名は、設定の `branchAgent` のエージェントに考えさせます（`src/repos/task.js`）。Claude は `claude -p` を使います。システムプロンプトを差し替え、ツール・MCP・スラッシュコマンド・ユーザーの設定（`--setting-sources ""`）・セッションの保存なしで動かします。一時フォルダで動かすのは、どこかのプロジェクトのエージェント向けガイドを読ませないためです。Codex は、リポジトリで `codex exec --sandbox read-only` を使い、名前の付け方の指示はプロンプトに入れます。Codex の設定とログインは、Codex に任せます。
  - どちらのプロバイダーも、Worktabs で有効な拡張に付属する実行ファイルを使います（`src/agents/agent-cli.js`）。PATH にある別の CLI は使いません。版のフォルダを覚えておかず、考えさせるたびに `extensions.json` を読み直します。Codex のチャットのプロキシも、同じ方法で実行ファイルを選びます。Codex は `bin/<プラットフォーム>-<アーキテクチャ>/codex`（Windows では `codex.exe`）を、Claude は対応する拡張の中の `resources/native-binary/claude`（Windows では `claude.exe`）を使います。考えさせる前に、プラットフォームの情報と、実行ファイルがあるかを確かめます。
  - WSL では、ディストリのホームとアーキテクチャを読んでから、そこの `~/.worktabs/extensions/extensions.json` を読みます。そこで動かすのは Linux の実行ファイルだけで、WSL の環境とログインを使います。code-server でエージェントをまだ起動していなくても使えます。Claude は `/tmp` で、Codex はリポジトリの Linux のパスで動かします。ファイルがなければ拡張の入れ方を、認証に失敗したらその環境でのサインインのしかたを出し、ほかの失敗は実行のエラーをそのまま出します。
  - プロンプトはコマンドの引数で渡し、標準入力は閉じます。付属の CLI が、パイプからの入力の続きを待たないようにするためです。使用量の上限による失敗が標準出力に出たときは、標準エラーに警告があっても、その失敗を出します。
- フォルダを選ぶ画面（`showOpenDialog`）と右クリックのメニューは、Windows のものをそのまま使います。Windows のライト／ダークの設定に従い、VS Code のテーマには従いません。

## UI の言語

アプリ自身の UI（メニュー・ダイアログ・サイドバー・メッセージ）は、コードの中に英語で、`t()` の引数として書きます（`src/i18n/`）。日本語は、その英語をキーにした表です（`src/i18n/ja.json`）。

- 言語は起動のときに 1 回だけ決めます。設定の `locale`（[config.md](config.md)）がアプリにある言語ならそれ、なければ英語です。空なら、OS の優先する言語に従います（Electron の `app.getPreferredSystemLanguages`）。
- 日本語の訳がない文言は、英語で出ます。文言の英語を変えると、前の訳は使われなくなり、訳し直すまで英語で出ます。`npm run translations` で、その両方がわかります。
- 文言の中の `{name}` は、出すときに埋めます。訳でも同じプレースホルダーを使います（テストで確かめています）。
- 語順が言語で違うので、文を部品から組み立てません。1 つの文を 1 つの文言にして、変わるところはプレースホルダーにします。英語で複数形が要るところは、単数を別の文言にします（`1 file …`、`{count} files …`）。
- ページ（サイドバーとダイアログ）は、スクリプトが動く前に、プリロードからメインプロセスに言語と表をもらいます（`i18n:get`）。`src/i18n/page.js` がそこからページの `t()` を作り、ページの HTML の文言を入れます。`data-i18n="英語"` の要素は、その訳を中身にします。`data-i18n-title`・`data-i18n-aria-label`・`data-i18n-placeholder` は、その属性に入れます。
- `src/sidebar/time.js` と `src/sidebar/checks.js` は、サイドバーでも、メインプロセスやテストでも動きます。そちらでは `src/i18n/` の `t()` を使います。
- 新しい worktree の最初の会話の入力欄に入れる指示（`src/repos/task.js` の `firstPrompt`）も、UI の言語で書きます。Claude がその言語で答えるようにするためです。

## サイドバーの作り直し

サイドバーの画面は、ツリーのまとめ役、依頼、ボタンを押している間の描画、GitHub のボタンをマウスを乗せたときに出す位置、幅の変更を `src/sidebar/sidebar.js` に持ちます。`src/sidebar/rows.js` は、注入した状態、選び出す関数、DOM の補助の関数、操作のコールバックから、リポジトリ・worktree・会話の行を作ります。行を描いても、データを読み始めることはなく、画面の操作のタイマーも持ちません。今までの画面のシナリオのテストと、行に絞ったテストは、同じ小さな DOM の材料を使います。

最初のタブの状態とリポジトリの一覧は、別々に読み込みます。実際のタブの更新が一度届いたら、遅れて来た最初のタブの返事は捨てます。こうすると、戻したタブや新しく開いたタブは「開いているリポジトリ」に残り、起動時の読み込みが終わるまでの間に、閉じたタブがまた出ることもありません。

`src/sidebar/model.js` は、明示した状態から、グループ、節の順番、マージ済みの worktree、絞り込んだ行、バッジを求めます。DOM も表示の設定も読みません。`src/sidebar/data.js` は、注入したホストの関数、時計、タイマー、変わったことを知らせるコールバックで、worktree・GitHub・PR の依頼をまとめて扱います。既定のタイマーは、ブラウザの関数を、コントローラーを受け手（レシーバー）として渡さずに呼びます。ブラウザはその受け手を受け付けないので、渡すとツリーが描かれなくなり、サーバーのバッジ、会話の状態、アーカイブした行が古いままになります。同じ依頼は、待っている読み込みを共有します。追い越された返事や無効になった返事が、新しい結果を置き換えることはありません。worktree の行と PR の結果は、読み込み中と一時的な失敗の間も出したままにし、成功して空だったときに消します。実行中の CI を読み直すのは、展開したグループだけです。読み直しでは GitHub と PR の読み込みを無効にし、画面を閉じるときは定期的な読み直しをやめて、遅れて来た返事を捨てます。マークアップ、表示の設定、メニュー、ポインターの動きは、描画の側が持ちます。

サイドバーは、何か変わるたびに、一覧の行とボタンをすべて作り直します（`src/sidebar/sidebar.js` の `render`）。クリックは、押した要素と離した要素に共通する親に届きます。押してから離すまでに行が作り直されると、押した行は画面から外れているので、クリックは行に届きません。

- ウィンドウが前に来ると、1〜2 秒のうちに何度も作り直します。前のタブの会話を見たことにし、タブのブランチを読み直し、展開しているリポジトリの worktree と PR・CI を読み直すためです。ほかのウィンドウが前にあるときにサイドバーの行を押すと、その押しでウィンドウが前に来るので、クリックが消えやすくなります。Claude の状態が変わったときや、CI が実行中のあいだの読み直しでも起きます。
- 作り直しの依頼はまとまって来るので、アニメーションの 1 フレームに 1 回まで、最新の状態で作り直します（`src/sidebar/press.js`）。メインプロセスも、タブの状態をサイドバーへ送るのはイベントループの 1 周に 1 回までです（`src/main.js` の `pushState`）。
- そこで、サイドバーの画面でマウスのボタンを押している間は、作り直しを待たせます（`src/sidebar/press.js`）。離すと、そのクリックを処理し終えてから（次のタスクで）、待たせた分を 1 回だけ作り直します。
- 離したことが画面に届かないこともあるので、ウィンドウからフォーカスが外れたときと、右クリックのメニューが出たときも待たせるのをやめます（macOS では、メニューが押したときに出て、離したことを受けます）。待たせるのは長くても 2 秒です。
- macOS では、後ろにあるウィンドウのクリックは、既定ではウィンドウを前に出すだけです。Windows と同じように押したものにも効くように、ウィンドウに `acceptFirstMouse` を付けます。タブの VS Code にも効きます。デスクトップ版の VS Code も、既定でこう動きます（設定の `window.clickThroughInactive`）。

## サイドバーの幅

サイドバーと各タブは、別々の `WebContentsView` です。右端をドラッグしてマウスがタブの上に出ると、マウスの動きがサイドバーの画面に届かなくなるおそれがあります。そこで、ドラッグしている間だけ、サイドバーの view をウィンドウ全体に広げます（`src/window/window-layout.js` の `startResize`）。

- タブの view は、サイドバーの view の下に置きます。ふだんは重ならないので、見た目は変わりません。ドラッグ中は、マウスがどこに行ってもサイドバーの画面が受けます。
- サイドバーの画面は、ドラッグした幅にサイドバーを描き、その先を透明にします。下のタブが見えます。広げる前に今の幅に固定し、戻ったのを確かめてから固定を外します。こうしないと、一瞬サイドバーがウィンドウ全体に広がって見えます。
- ドラッグ中に大きさを変えるのは、前に出ているタブだけです。Chromium がマウスの動きを 1 フレームに 1 回までにまとめて画面に送るので、変えるのもそれまでです。VS Code の描き直しは、ウィンドウの大きさを変えるときと同じです。隠れているタブは、離したときにまとめて変えます。
- 広げたままになると、透明な画面がタブへのクリックをすべて受けてしまいます。そこで、離したことに画面が気づけなくても終えます。ボタンを押していないマウスの動き、フォーカスが外れたこと（ダイアログが出た、ほかのウィンドウに切り替えたなど）、サイドバーの画面の読み込み直しとクラッシュです。
- ドラッグした幅は `window.json` に持ちます。設定ファイルは人が書くものなので、ドラッグのたびには書き換えません。設定の `sidebarWidth` は既定の幅で、ダブルクリックでこれに戻ります。

## エクスプローラーのタブ（Windows）

Windows には、エクスプローラーの既存のウィンドウにタブを足す API がありません。`claude-wrap.exe --explore`（項目を選ぶときは `--explore-select`）が次の順に開きます。

- 一番手前のエクスプローラーのウィンドウ（`CabinetWClass`）を探し、そのタブ部分（`ShellTabWindowClass`）に、エクスプローラー自身の「新しいタブ」ボタンと同じコマンド（`WM_COMMAND 0xA21B`）を送ります。
- できたタブを `Shell.Application` から目的のフォルダに移し、必要なら項目を選び、ウィンドウを手前に出します。Windows は、手前にあるプロセス（アプリ）が起動したプロセスには、ほかのウィンドウを手前に出すことを許します。拡張ホストが起動したプロセスは許されないことがあるので、補助拡張からの依頼もアプリが起動します。
- ウィンドウがないとき、またはどこかで失敗したときは、`explorer.exe` で新しいウィンドウを開きます。
- Windows の設定の「デスクトップのフォルダーと外部フォルダーのリンクを新しいタブで開く」（`OpenFolderInNewTab`）は使いません。Windows 全体の設定で、オフのままでも動くようにするためです。

## GitHub のボタン

URL は `git remote get-url`（origin、なければ最初のリモート）から作ります（`src/repos/github.js` の `readRemote`）。次のホストを GitHub とみなします。

- github.com、`github.` で始まるホスト（GitHub Enterprise Server）、`<テナント>.ghe.com`（GitHub Enterprise Cloud のデータ所在地）
- 設定の `githubHosts` に書いたホスト（[config.md](config.md)）
- gh がサインインしているホスト（`gh auth status --json hosts`。`--json` のない古い gh は、`gh auth status` の「Logged in to <ホスト>」から読みます）。トークンが切れていても、gh に登録したホストは GitHub とみなします

ほかに、`gitlab.com` と `gitlab.` で始まるホストを GitLab、`bitbucket.org` と `bitbucket.` で始まるホストを Bitbucket とみなし、リポジトリの行のアイコンに使います（[usage.md](usage.md#リポジトリ)）。どれでもなければ「そのほか」です。

- SSH の URL（`git@host:o/r`、`ssh://`）は、`ssh -G <ホスト>` の `hostname` で本当のホスト名に読み替えてから判定します。`~/.ssh/config` の `Host github-work`（`HostName github.com`）のような別名で、アカウントを使い分けることが多いためです。`git remote get-url` は `url.<base>.insteadOf` は読み替えますが、SSH の別名は読み替えません。`ssh -G` は接続せずに、使う設定を出すだけです。
  - ssh と gh は、リポジトリのある場所で動かします（WSL のリポジトリは WSL の中）。場所とホストごとに 1 回だけ聞いて覚え、上端の「リポジトリ一覧を更新」で聞き直します。一覧のすべてのリポジトリのリモートを読むので、リポジトリごとに聞くと遅くなるためです。
  - ssh がない・失敗したときは、URL のホスト名で判定します。
  - gh は、ホスト名でも設定でも分からないホストのときだけ聞きます（GitLab・Bitbucket と分かるホストでも聞きません）。`gh auth status` は、トークンを確かめるのに 1 秒ほどかかります。
- HTTPS の URL のポートは、ページの URL に残します（`https://github.example.com:8443/o/r`）。SSH のポートは Web のポートではないので落とします。
- ssh.github.com・altssh.gitlab.com・altssh.bitbucket.org（443 番ポートの SSH）は、それぞれのサービスのホストとみなします。

- リポジトリの行のアイコン（GitHub・GitLab・Bitbucket など）と公開範囲のアイコンは、メインプロセスが一覧のすべての git リポジトリについて読みます（`src/main.js` の `readVisibilities`）。畳んだままの行にも出すためです。
  - リモートは、一覧に初めて載ったときだけ読みます（同時に 8 個まで。`src/repos/github.js` の `readRemotes`）。上端の「リポジトリ一覧を更新」では、すべて読み直します。リポジトリが数百あると、読むたびに git を数百回（WSL のリポジトリは WSL の中で）呼ぶことになるためです。
  - 読んだリモートは、公開範囲を聞く前にサイドバーに送ります（`repoMessage` の `providers`）。サイドバーは、GitHub でないと分かっているリポジトリの行では、畳んでいても、アイコンに乗せても GitHub のボタンを出しません。worktree の追加のダイアログも、これで上の欄を「やること」だけにするかを決めます（[worktrees.md](worktrees.md#追加)）。
  - 公開範囲は、一覧を読み直すたびに（起動したとき・更新ボタン・「リポジトリを追加…」のあと）、`gh api graphql` で聞きます（`src/repos/github.js` の `repoVisibility`）。gh を動かす場所（WSL のリポジトリは WSL の中の gh）とホストごとに 1 回で、100 個ずつまとめます。
  - 問い合わせは、リポジトリごとに `repository(owner:, name:) { visibility url }` を並べたものです。名前を変えたリポジトリや、ほかの owner に移したリポジトリも、古い名前のまま答えが返ります。`resource(url:)` は、これに `null` を返します。`url` は、GitHub が今そのリポジトリを置いている URL です。リモートの URL と違えば `repos.json` の `remotes` に `current` として残し、クローン済みかを比べるのに使います（下記「[クローンしていないリポジトリ](#クローンしていないリポジトリ)」）。
  - 消えたリポジトリや見られないリポジトリがあると、答えにエラーが入り、gh は失敗で終わります。それでも gh は答えを標準出力に書くので、ほかのリポジトリの分はそこから読みます。`data` のない答え（サインインしていないなど）は失敗として扱い、前回の分を残します。
  - プロバイダー・URL・公開範囲は `repos.json` の `remotes` に残し、次の起動ではまずそれを出します。前の版が `github` に残した分は、ホスト名だけで判定したもの（SSH の別名を取り違える）なので読みません。
- Approve 済みでマージしていない自分の PR（リポジトリの行のアイコンの赤い点）も、メインプロセスが読みます（`src/main.js` の `readApproved`、`src/repos/github.js` の `approvedPulls`）。畳んだままの行にも出すためです。
  - 問い合わせは `viewer { pullRequests(states: OPEN, first: 100) }` で、gh がサインインしているアカウントのオープンの PR を、リポジトリを問わず読みます。gh を動かす場所（WSL のリポジトリは WSL の中の gh）とホストごとに 1 回で、リポジトリの数によりません。worktree のブランチから読まないのは、PR のブランチの worktree が手元にないこと（別の端末で作った、先に消した）があるためです。
  - 答えの PR の `repository.url`（マージ先のリポジトリ）を、リモートの URL と、名前を変えたリポジトリの今の URL（`current`）に照らして、リポジトリに振り分けます（`repoKey`）。サイドバーには `repoMessage` の `approved` で送ります。
  - Approve 済みかは `reviewDecision` で決めます（`isApproved`）。レビューを必須にしていないブランチでは、これが `null` です。そのときは `latestOpinionatedReviews(writersOnly: true)`（書き込みのできる人ごとの最後のレビュー。GitHub の判定に数えるもの）に `APPROVED` があり、`CHANGES_REQUESTED` がないことで決めます。検索の `review:approved` は、レビュー必須でないリポジトリでどう効くかがはっきりしないので使いません。ドラフトと、アーカイブしたリポジトリの PR は除きます。
  - 読むのは、公開範囲を聞いたあと（名前を変えたリポジトリの今の URL が分かってから）・5 分おき・ウィンドウが前に来たとき（前の読み込みから 1 分たっていれば）・Claude が push やマージをした 10 秒後と 30 秒後（`startsChecks`）です。Approve は GitHub で人がするので、アプリの中の出来事では気づけません。ウィンドウはタブで作業している間ずっと前にあるので、5 分おきにも読みます。1 回の問い合わせは、GraphQL の上限（1 時間に 5000）の 1 ほどです。
  - WSL の場所は、一覧を読み直したあと以外は、ディストリが動いているとき（`wsl.exe -l --running -q`。これは WSL を起動しない）だけ読みます。5 分おきに読むと、止まっている WSL を起動し続けるためです。読まなかった場所と、gh が失敗した場所は、前の分を残します。
  - gh がサインインしていないホスト（`gh auth status`）には聞かず、点も出しません。gh がない環境で、5 分おきに失敗し続けないためです。
  - `repos.json` には残しません。マージされたものが、次の起動で出てしまうためです。
  - サイドバーは、展開したリポジトリの worktree の行が読んだ PR（`branchPulls`）がマージ済み・クローズ・ドラフトなら、その PR を点から外します（`src/sidebar/pulls.js` の `approvedOf`）。worktree の行は、何かをするとすぐに読み直すためです。
  - 点は、リポジトリのアイコンを包む要素（`.provider-box`）に、`position: absolute` で重ねます。行の幅は変わりません。点は `pointer-events: none` なので、アイコンに乗せたときの GitHub のボタンの動きは変わりません。アイコンには点の周りに穴を開けます（`mask-image`）。点に背景色の縁を付けると、マウスを乗せた行やアイコンの背景の色と合わないためです。包む要素はプロバイダーによらないので、GitLab・Bitbucket の MR・PR を読むようにしたら、同じ点を出せます。

- リモートと既定のブランチは、リポジトリを初めて展開したときに 1 度だけ読みます。サイドバーの上端の「リポジトリ一覧を更新」で読み直します。
- 「このブランチの PR」は `gh pr view <ブランチ>` で PR を探し、見つからなければ（gh がない場合も）PR の作成画面（`/compare/<ブランチ>?expand=1`）を開きます。既存の PR があれば、作成画面にもそのリンクが出ます。
- worktree の行の PR と CI は、リポジトリごとに 1 回の `gh api graphql` で読みます（`src/repos/github.js` の `branchPulls`）。
  - 問い合わせは、worktree のブランチごとに `pullRequests(headRefName: <ブランチ>)` を並べたものです。`gh pr list` でリポジトリの PR を一覧すると、件数の上限（`--limit`）より古いものが漏れます。ブランチを名指しすれば、PR がいくつあっても漏れません。
  - PR の選び方は `gh pr view <ブランチ>` と同じです。フォークから出した PR（`isCrossRepository`）は除き、オープンのものを、なければ一番新しいものを選びます。
  - PR から作ったブランチ（git の設定に `worktabs-pull` があるもの）は、その PR も `resource(url: <PR の URL>)` で読み、あればそれを選びます。フォークからの PR も、PR と違う名前のブランチも、これで出ます。
    - `pullRequest(number: <番号>)` で読まないのは、リポジトリにない番号（あとで origin を別のリポジトリに変えたなど）があると、問い合わせ全体がエラーになり（gh も失敗で終わる）、ほかのブランチの PR まで出なくなるためです。`resource` は、ない番号でもエラーにならず `null` を返します。
    - その PR がなければ、ほかのブランチと同じに、ブランチ名で探した PR を選びます。
  - CI の結果は、コミットの `statusCheckRollup` です。`SUCCESS` は成功、`FAILURE`・`ERROR` は失敗、`PENDING`・`EXPECTED` は実行中です。コミットの `statusCheckRollup` には、そのコミットで動いたワークフローが、イベント（PR・ブランチの push・タグの push）を問わず入ります。なので、どのコミットを読むかで、何の CI かが決まります。

    | 行 | 読むコミット |
    | --- | --- |
    | オープンの PR | PR の最後のコミット（`commits(last: 1)`） |
    | マージ済みの PR | PR の `mergeCommit`（main への push の CI） |
    | PR がない（既定のブランチ・ブランチのない HEAD を含む） | worktree の HEAD（`git worktree list` の `HEAD`）を `object(oid:)` で |

  - HEAD は、すべての worktree の分を同じ問い合わせに入れます（`h0`, `h1`, ...）。PR があるかは答えを読むまで分からないためです。GitHub にないコミット（push していない）は、エラーにならず `null` が返ります。
  - チェックごとの名前・結果・時刻は、`statusCheckRollup.contexts` から 30 個まで読みます（`gh pr checks` と同じ項目）。GitHub Actions のジョブは「ワークフロー名 / ジョブ名」で出します。
  - HEAD のコミットでは、チェックスイートの `branch`（`refs/heads/main`、`refs/tags/v0.2.0`）で、その行のブランチへの push のものだけを残します（`src/sidebar/checks.js` の `ownChecks`）。タグのものは、既定のブランチの行にだけ残します。残したものから、成功・失敗・実行中をまとめ直します。main から作ったばかりのブランチは HEAD が main と同じコミットなので、こうしないと main の CI が出ます。
  - マージのコミットと HEAD のコミットの CI は、チェックが最後に始まるか終わってから、成功は 1 時間、失敗と実行中は 1 日だけ出します（`recentChecks`）。マージや pull からの時間ではなく、チェックの時刻で決めるのは、古いコミットに後からタグを打ったリリースや、やり直し（re-run）も出すためです。判断はサイドバーが描くときにするので、読み直さなくても、時間がたてば消えます（描き直したとき）。
  - 1 回の問い合わせは、GraphQL の上限（1 時間に 5000）の 1〜3 ほどです（worktree が 10 個で 3）。ウィンドウが前に来るたびに読まないよう、前の読み込みから 15 秒は読み直しません。Claude の作業が終わったとき（PR を作ったかもしれない）は、すぐに読みます。出している CI が実行中のあいだは 1 分おきに読みます。
  - Claude が push などをすると（PostToolUse のフックの `tool_input.command` が `git push`・`gh pr create`・`gh pr merge`・`gh release create` などのとき。`src/repos/github.js` の `startsChecks`）、その 10 秒後と 30 秒後にも読みます。push の直後は、GitHub がまだチェックスイートを作っておらず、`statusCheckRollup` が空のことがあるためです。
  - gh は、リポジトリのある場所で動かします（WSL のリポジトリなら WSL の中の gh）。
  - PR の最後のコミット（`headRefOid`）も読みます。マージ済みで、それが worktree の HEAD と同じなら（`src/repos/github.js` の `mergedAtHead`）、ブランチのコミットはどれもマージした PR にあります。行のゴミ箱を常に出し、削除の確認でブランチの削除を既定でオンにします（[worktrees.md](worktrees.md#削除)）。
- worktree の削除の確認では、そのブランチの PR だけを同じ問い合わせで読み直します（`src/repos/worktree-removal.js` の `removalPull`）。行の PR は古いことがあり、タブの右クリックからの削除はサイドバーを通らないためです。待つのは 5 秒までで、それを過ぎると gh を止めて、PR なしで確認を出します。worktree のフォルダがないこともあるので、gh はリポジトリ（primary）の場所で動かします。

## クローンしていないリポジトリ

サイドバーの「クローンしていないリポジトリ」（[usage.md](usage.md#クローンしていないリポジトリ)）は、gh に聞いたアカウントのリポジトリから、一覧のリポジトリを引いたものです。照らし合わせとクローン先の求め方は `src/repos/clone.js`（Electron なしでテストできる）、gh への問い合わせは `src/repos/github.js` の `ownedRepos` にあります。

- 読み方: gh がサインインしているホスト（`gh auth status`。GitHub Enterprise を含む）ごとに、`gh api --hostname <ホスト> --paginate 'user/repos?affiliation=owner,organization_member&per_page=100'` を 1 回呼びます。
  - 自分が owner のリポジトリ（自分のフォークを含む）と、自分が入っている org のリポジトリが、1 回で取れます。collaborator として入っているだけのほかの人のリポジトリは入りません。
  - `gh repo list` は使いません。owner ごとに 1 回ずつ呼ぶことになり、`--hostname` もない（ホストは環境変数 `GH_HOST` で替える）ためです。`gh api` なら、公開範囲の問い合わせと同じく `--hostname` で GitHub Enterprise にも聞けます。GitHub Enterprise Server の REST の道（`/api/v3`）は、gh が決めます。
  - `--jq` で、owner（`login` と、`User` か `Organization` か）・名前・`html_url`・フォークか・アーカイブか・公開範囲・説明・最後の push だけを 1 行ずつ出させます（`readOwnedRepos`）。アーカイブしたものは捨てます。owner と名前は、コマンドラインやパスに入るので、英数字と `.`・`_`・`-` だけのもの（`-` で始まらない、`.`・`..` でない）だけを受け取ります。
  - gh は Windows・macOS の gh です（WSL の中の gh には聞きません）。gh がない・サインインしていないときは、何も出しません。聞けなかったホストは、前回の分を残します（`mergeOwned`）。
- いつ読むか: 一覧を読み直すたびに、リモートと公開範囲を読むのと一緒に読みます（`src/main.js` の `readVisibilities`）。gh への問い合わせはリモートを読み始めるときに始めますが、結果を取り込むのは、リモートと公開範囲（今の URL）を読み終えてからです。初めての起動で、クローン済みのものが未クローンに出ないようにするためです。結果は `repos.json` の `owned` に残し、次の起動ではまずそれを出します。
- 照らし合わせ（`unclonedGroups`）: サイドバーに送るたびに、`owned` から次のものを引きます。どれも、`<ホスト>/<owner>/<名前>` を小文字にして比べます（ポートは除く）。
  - 一覧の git リポジトリのリモートの URL（Windows と WSL の両方）と、GitHub が答えた今の URL（`current`）。名前を変えた・owner を移したリポジトリは、リモートの URL が古いままでも、今の URL で一致します。
  - 一覧のリポジトリと、開いているタブのリポジトリのフォルダの、最後の 3 つの名前。ghq の並び（`.../<ホスト>/<owner>/<名前>`）のフォルダは、リモートを読めなかった（WSL が応えないなど）・まだ読んでいない（アプリの外でクローンしたばかり）ときも、これで一致します。
  - `hiddenGithubOwners` の owner も、ここで外します。
- 並べ方: owner ごとにまとめ、自分のアカウント（github.com が先）、org（名前順）の順にします。owner の中は、最後に push した順です。
- クローン（`startClone`）:
  - クローン先の候補は、ここ（Windows・macOS）と、Windows では WSL のディストリです。ディストリは、`repoSources` で読んでいるもののうち、一覧にリポジトリがあるものと、ghq が入っているもの（一覧を読むときに、`ghq` があれば印を出すようにした。`repoCatalog` の `ghq`）です。
  - ghq があれば（`ghq root` が動けば）、`ghq get [-p] <ホスト>/<owner>/<名前>` を動かし、`ghq list --full-path` からクローンしたフォルダを探します。`ghq.<url>.root` で、`ghq root` と違う root に入ることがあるためです。
  - ghq がなければ、クローン先のダイアログ（`src/dialog/clone.js`）で聞いて、`git clone -- <URL> <フォルダ>` を動かします。git は、フォルダのある場所（WSL のフォルダなら、そのディストリの中）で動かします。
  - https か SSH かは、`gh config get git_protocol -h <ホスト>` で決めます（`gitProtocol`。gh がなければ https）。`gh repo clone` と同じ決め方です。
  - `GIT_TERMINAL_PROMPT=0` を付けて動かします。端末のないところで git がユーザー名を聞くと、時間切れ（10 分）まで待ってしまうためです。Git Credential Manager は、自分の画面で聞きます。WSL の中では、環境変数が渡らないので、`env GIT_TERMINAL_PROMPT=0 <コマンド>` で動かします（`runAt` の `env`）。
  - 終わったら、そのフォルダを一覧に足し、リモートの URL も分かっているものとして `remotes` に入れます（`addClonedRepo`）。こうすると、一覧を読み直すのを待たずに、その行は「クローンしていないリポジトリ」から消えます。
- クローン先のダイアログの候補（`cloneRoots`）: クローン先の場所（Windows か、そのディストリ）の一覧のリポジトリから求めます。
  - フォルダの最後の 3 つの名前が、リモートの `<ホスト>/<owner>/<名前>` と同じなら、ghq の並びとみなし、`<root>` を候補にします（同じ並びでクローンする）。リモートが GitHub でない・読んでいないときは、3 つ上の名前がホスト名らしい（`.` を含む）かで決めます。
  - それ以外は、親のフォルダを候補にします（`<親>/<名前>` にクローンする）。
  - リポジトリの多い場所から並べます。最後にクローンした場所（`cloneRoot`）が同じ場所にあれば、それを最初に欄に入れます。「参照…」で選んだフォルダと `cloneRoot` は、候補にあればその並びに、なければ、その下にホストのフォルダ（`github.com` など）があるときだけ ghq の並びにします。

## claude のラッパー

`claudeCode.claudeProcessWrapper` に、claude を包むプログラムを設定します。OS ごとに別のものですが、コマンドラインは同じで、同じテストを通します（`test/wrap-fixture.js`）。

| OS | ラッパー |
|---|---|
| Windows | `native/claude-wrap.exe`（`native/ClaudeWrap.cs` を Windows 付属の csc.exe でビルド） |
| macOS | `<データフォルダ>/bin/claude-wrap`（`src/agents/mac-claude-wrap.js` を呼ぶ sh のスクリプト） |
| WSL | `~/.worktabs/bin/claude-wrap`（`src/wsl/wsl-claude-wrap.sh`。使用量は拾いません） |

- macOS のラッパーは、拡張から実行ファイルとして起動されます。頼れる node が PATH にないので、アプリが起動のたびに次の 2 つをデータフォルダに書き出します。パスが変わっても（アプリを移しても）追いつきます。
  - `mac-claude-wrap.js`: ラッパー本体。パッケージ版では asar の中にあり、素の node からは読めないので、外に写します。
  - `claude-wrap`: それをアプリ自身のバイナリ（`ELECTRON_RUN_AS_NODE=1`）で実行する sh のスクリプト。code-server の node でもよいのですが、フックの設定を書く時点ではまだ用意できていません。この変数はラッパー限りで、claude には渡しません。
- Windows のラッパーだけが `--explore` を持ちます（下の「エクスプローラーのタブ」）。ほかの OS では、アプリがシェルに任せます。

## hooks

- 拡張が claude を起動するときに、このラッパーが `--settings <hook-settings.json>` を足します。hooks が効くのはアプリが管理するセッションだけで、`~/.claude/settings.json` もリポジトリの `.claude/` も変更しません。
- SessionStart だけは http hook にできないので、`claude-wrap --hook` が転送します。
- ラッパーは自分のプロセス ID を `WORKTABS_PROC_ID` として claude に渡し、hooks はそれをヘッダー（`X-Wrapper-Proc`）に付けます。拡張は、パネルで開いた会話ごとに claude を 1 つ起動するので（1 つのパネルの中でも、会話ごとに別の claude です）、これでパネルごとの会話を見分けられます。
- 受信は `127.0.0.1` のランダムなポートで、起動ごとのトークンで検証します。

## 使用量

拡張は claude を stream-json で起動します。claude はその出力に、応答のヘッダーから読んだ使用量を `rate_limit_event` として書きます（`rate_limit_info.unifiedWindows` の `five_hour`・`seven_day`）。拡張も、これでパネルに使用量を出しています。

- ラッパーは claude の標準出力をパイプで受け、中身を変えずにすぐ拡張へ流します。そのうち `rate_limit_event` の行だけを、hooks の受信口（`/usage`）にも送ります。標準入力と標準エラーは、今までどおり claude に継がせます。
- claude の statusLine のコマンドは、ターミナルの画面でしか呼ばれないので、拡張の claude では使えません。ドキュメントにない OAuth の API（使用量の取得）も使いません。
- 受け取った値は `hooks.log` にも残します。

Codex の利用枠も、会話の状態と同じく、拡張が持つ app-server のプロキシを使います。プロキシは、対応している [`account/rateLimits/read` と `account/rateLimits/updated` のプロトコル](https://learn.chatgpt.com/docs/app-server)を、自分では依頼を出さずに見るだけです。

`src/agents/usage-polling.js` は、起動時に拡張の準備ができたあと、5 分ごと、Codex のアカウントのイベントのあとに、利用枠を読む予定を立てます。読むのはプロバイダーごとに 1 つずつで、重なった依頼は、待っている 1 回のやり直しにまとめます。読めなくても、予定は止まりません。終了すると読み込みを取り消し、待っているやり直しも消します。予定を立てる部分とトラッカーへの再生は Electron なしで動くので、アカウントの切り替えや重なった読み込みをテストで試せます。

`src/agents/usage-refresh.js` は、読むたびに、有効なホストの拡張の実行ファイルを求めます。WSL だけのアカウントは自動取得しません。20 秒の期限は、実行ファイルを求めることと、補助のプロセスとの接続の全体にかかります。取り消しや時間切れのあとに実行ファイルが見つかっても、補助のプロセスは起動しません。Codex は、自分用の短い間だけの app-server を初期化し、アカウントの識別を読んでから、サブスクリプションの上限を読みます。`account/updated` の通知が来ると、待っている応答は無効になるので、元の期限の中で、新しい ID でアカウントの識別と利用枠をもう一度依頼します。待っている応答より新しい利用枠の通知が来たときも、全体を読み直します。サブスクリプションの識別がなければ、匿名の利用枠を読まずに、失敗として表示します。Claude は、stream-json の `initialize` と、実験的な `get_usage` の制御リクエストだけを、`skip_behaviors` を付けて送ります。hooks・tools・MCP・スラッシュコマンド・プロジェクト設定・会話の保存は無効にします。どちらの補助のプロセスも、ユーザーのメッセージを送らず、モデルのターンも始めません。応答からは決まった項目だけを取り出し、診断出力と、アカウントと使用量の応答の全体は捨てます。対応しない版の Claude は、失敗として表示し、あとでやり直します。Claude を最後まで読めたときは、すべての枠を置き換えます（結果にない枠は消えます）。新しい実際のイベントより前に始めた読み込みが、それを上書きすることはありません。有効なプロバイダーの欄は、値がリセットされた・期限が切れた・読めなかったときも残します。

Codex の再生では、アカウントと利用枠のイベントが受け入れられたかを、1 つずつ確かめます。プロトコルの応答があっただけでは、表示を更新できたことになりません。利用枠が受け入れられ、知っている今の枠が入っている必要があります。空のスナップショットや知らない形のスナップショットは、取得できないままです。実際のアカウントのイベントを受け入れるたびに、メモリの中の世代（epoch）を進めます。そのイベントより前に始めた裏の読み込みは、時刻が同じイベントでも、再生の前に退けます。実際のアカウントの通知は、新しい読み込みを順番待ちに入れます。こうして、遅れて来たホストの読み込みが、前のアカウントを生き返らせたり、新しいアカウントの確認を取り消したりしないようにします。退けたスナップショットと失敗した読み込みでは、古いスナップショットを受け取った時刻を延ばしません。

下端の欄は、裏で読んでいる最中であることを、古い利用枠のデータとは分けて出します。失敗、時間切れ、退けた更新は、古い枠の横に出したままにします。プロバイダーと行のツールチップには、最後に利用枠を受け取った時刻、最後に更新を試した時刻、次に試す予定の時刻が出ます。`logs/usage-refresh.log` に残すのは、プロバイダー、時刻、結果、決まった失敗と退けた理由の分類、受け入れた数、最後に利用枠を受け取った時刻、次の予定の時刻だけです。CLI のエラーと標準エラーを写すことはありません。アカウントのメールアドレス、識別のハッシュ、トークン、応答の全体、利用枠の中身はログに残しません。診断の書き込みに失敗しても、定期的な読み込みは止まりません。

- `src/codex/codex-quota.js` が取り出すのは、primary と secondary の割合、報告された枠の長さ、リセットの時刻、あれば枠（bucket）の ID と名前だけです。複数の枠を読んだ結果は、互換のための 1 つの枠の見え方より優先します。クレジットと、リセットのクレジットの詳細は捨てます。
- プロキシは、利用枠の依頼の順番を覚え、アカウントの変化を見ます。古い読み込みの応答が、新しい通知や読み込みを置き換えることはありません。ログイン・ログアウト・アカウントの更新より前から待っている読み込みが、新しいアカウントの利用枠になることはありません。
- アカウントを見て出すのは、認証の方式と、ドキュメントにあるアカウントのメールアドレスのハッシュだけです。メモリの中で同じアカウントかを比べるのに使います。トークンの項目は見ず、メールアドレス、ログインの引数、認証の応答の全体、認証の URL は渡しません。
- 必要なものだけにしたアカウントと利用枠のイベントは、トークンで守った受信口の `/codex` に送ります。WSL でも、今の転送の道を通ります。順番待ちは、アカウントの切れ目と枠の更新を保ちます。これらのイベントで会話の行はできず、`hooks.log` にも書きません。
- `src/codex/codex-usage.js` は、アカウント全体のスナップショットを、Claude の `UsageTracker` とは別にメモリに持ちます。タブをまたいで見た時刻を比べ、割合を足し合わせることはしません。全体を読んだときは枠の一覧を置き換え、通知では報告された枠だけを更新します。いつものアカウントの通知では、出しているスナップショットはそのままにし、アカウントを確かめ直すまで、届いた利用枠を止めておきます。同じアカウントなら、新しい利用枠が届くまでスナップショットを残し、違うアカウント、ログイン、ログアウト、サブスクリプションでない方式なら消します。失敗した読み込みでは、空のスナップショットを出さず、新しさも更新しません。
- 下端の欄に出すのは、最後に見たアカウントのものです。知っている同じアカウントなら、いくつものタブから報告できます。アカウントの報告がないときは、最後のアカウントの切れ目よりあとの、条件に合うスナップショットだけを使います。これは控えめな表示で、複数のアカウントを並べる表示ではありません。
- 項目がない、リセットの時刻を過ぎた、15 分より古いスナップショットのときは、割合を不明にします。タイマーが 1 分ごとに、期限切れ、古い状態、時刻の表示を更新します。下端の欄は両方のプロバイダーに名前を付け、どちらも**使った**割合を出します。Codex の `usedPercent` は、裏返す必要がありません。

## 会話の状態

`src/conversations/conversation-store.js` は、会話の状態、プロバイダーごとのプロセスとの結び付き、順番、未読とアーカイブの印、移動のための情報を持ちます。時計は注入し、ファイルの読み込み、プロセスの確認、タイマーの仕事はしません。`src/conversations/claude-observer.js` は、transcript の監視とローカルのプロセスの定期的な確認を、注入した読み取り、生きているかの確認、タイマーで、明示して取り付けます。バイトの位置と行の途中までのバッファはストアの外に持ち、初めて取り付けたときは末尾の決まった量だけを読み、ターンが始まったときは古い中断の記録を無視します。題名の記録が揃ったときと、状態の移り変わりを見たときに、ストアを更新します。transcript が一時的に読めないときは、位置を進めずにやり直します。開始と停止は何度呼んでも同じ結果で、終了すると監視をやめます。WSL のプロセスの終了は、今までどおりディストリのエージェントから届きます。`HookServer` は、今までどおり `src/conversations/hooks.js` にある、認証付きの HTTP の橋渡しです。そこから export する `SessionTracker` は、ストアとオブザーバーを組み合わせた、互換のためのアダプターです。

`session_id` ごとに状態を持ち、タブにはそのうち最も緊急なものを出します。

Claude Code では、上で説明した hooks を使います。Codex でも、バッジ、経過時間、数、未読の結果、アーカイブ、止めるときの警告に、同じ `ConversationStore` を使います。Codex のアダプターは、その拡張の会話を見られない別のエージェントを起動するのではなく、Codex の拡張が持つ app-server を見ます。

### Codex の app-server

`src/conversations/conversation-navigation.js` は、Codex の会話を前に出せたかを、画面に出ている（マウントされて見えている）ローカルのスレッドの情報から確かめます。作業中のスレッドで権限の操作が無効になっていても確かめられます。URI を送れても、それは依頼にすぎず、頼んだスレッドを確かめるまで未読は消しません。何も出ない、どれか決まらない、対応していない、止まったままの画面は、15 秒の期限が来ると移動の警告を出します。タブやサーバーの起動が変わったときと、新しく前に出すときは、遅れて来た結果を無効にします。

新しい worktree のタスクには、`src/conversations/first-conversation.js` を使います。補助拡張は Codex を有効にして `chatgpt.newChat` を実行し、実行したことを返します。モデルへの問い合わせはしません。そのあと、時間を区切った確認で、画面に出ている権限の情報から、ローカルの新しい会話であることと、見えている空のリッチテキストの入力欄が 1 つだけあることを確かめます。ネイティブの `insertText` で、書き換えられる下書きを入れます。Enter は押さず、送信のコールバックも呼びません。知らない形、すでにある下書きやスレッド、入力を受け付けなかったとき、起動の失敗では、タスクをコピーできるやり直しのダイアログに、タスクを出します。Claude は、今までどおり拡張のコマンドの、入力欄に入れる引数を使います。

- code-server を起動する前に、インスタンスの管理する設定 `chatgpt.cliExecutable` をプロキシにします（`src/codex/codex-launch.js`、`src/codex/codex-wrap.js`）。本当の CLI は、有効な `OpenAI.chatgpt` 拡張に付属する実行ファイルです。チャットとブランチ名の提案は、`src/agents/agent-cli.js` の実行ファイルの選び方を共有します。ブランチ名の提案は、実行ファイルを直接動かし、チャットの会話のイベントは送りません。拡張を入れる・更新する・インポートし直す・戻すと、CLI の版もそれで決まります。Worktabs が CLI を別に入れて管理することはありません。
- Windows では、`native/CodexWrap.cs` が code-server の node でプロキシを起動します。拡張が起動役を止めると、ジョブオブジェクトが node、app-server、その子プロセスを止めます。macOS と WSL では、実行できるシェルスクリプトが、code-server の node でプロキシを動かします。
- プロキシは、引数、標準入力、標準出力、標準エラー、終了コードをそのまま渡します。改行で区切った JSON のプロトコルを、両方の向きで見ます。app-server への依頼は出さず、承認の判断も送りません。認証と承認は Codex の拡張のままです。
- `src/codex/codex-events.js` は、`thread/*`・`turn/*`・`item/*` のイベントを状態に対応させます。ターンが始まると `working`、終わると `done`、失敗すると `error`、中断すると `idle` です。完了のあとに実行時の状態が `idle` になっても、結果は出したままです。知らない実行時の状態は `working` とみなすので、新しい版の拡張で、作業中のスレッドが待機中に見えることはありません。ツールの失敗と、やり直すエラーでは、ターンは終わりません。
- app-server が拡張の `initialize` に答えると、プロキシは `codex-observer` を 1 回送ります。そのタブは、code-server が再起動するまで、見えているものとして数えます。更新の前に、Codex の拡張が動いている（補助拡張の `/codex-active`）のに見えていないタブは、閉じる必要があります。拡張が、プロキシを通さずに CLI を起動したかもしれないためです。ほかのタブは、Claude のタブと同じく、作業中と承認待ちの会話と未保存の編集がなくなるのを待つだけです。
- コマンド・ファイル・権限・ユーザーの入力・MCP の elicitation の依頼で、会話は `waiting` になります。依頼は、答えが出るまで（またはその item が終わるまで）待ちのままです。ほかの item のイベントで、同時に出ている承認が消えることはありません。ターンが終わると待っている依頼は消え、古いターンのイベントで新しいターンが終わることはありません。
- トークンで守った受信口の `/codex` に送るのは、会話の情報と、必要なものだけにした利用枠とアカウントの状態だけです。順番どおりに、プロトコルのパイプとは別に送ります。認証の応答の全体、認証情報、流れてくる出力、一覧した履歴は送りません。WSL では、エージェントがこの受信口に転送し、作業フォルダを Windows のパスに直します。
- 1 つのプロセスは、いくつものスレッドを同時に持ちます。別のスレッドを読み込んでも、前の行は消しません。プロセスが終わると、持っていたスレッドを手放しますが、使ったスレッドは待機中の履歴の行として残します。ほかのプロセスが持っているスレッドは、その状態のままです。同じスレッドを Worktabs の別のタブで開くと、状態は別々です。Codex の ID が Claude のセッション ID とぶつかることはありません。
- 新しい空のスレッドは、使うまで行がありません。再開したスレッドには、待機中の行ができます。題名はスレッドの名前から取ります。読み込んだターンの最後のユーザーのメッセージの item を、スレッドのプレビュー（最初のプロンプトのことがあります）より優先します。古い再開のスナップショットが、実際のターンやプロンプトを置き換えることはありません。
- 仕事を任された子は、`parentThreadId`、構造化された `subAgent.thread_spawn` の source、完了した spawn・wait の協調の item、親のターンにある種類が `started` の `subAgentActivity` の item のどれかで見分けます（新しいサーバーは、子を起動したことをこの形で知らせ、子自身のイベントには source がありません）。ほかの種類の activity は、知っている子を更新するだけです。祖先を指すことがあるためです。親の ID、ニックネーム、役割、エージェントのパスは、オブザーバーとストアを通り、移動のための情報と一緒に保存します。サイドバーはサブエージェントの札を付け、それぞれを親の下に入れます。クリックすると、今までどおり子自身のスレッドを開きます。作業中・承認待ちのバッジと、止めるときの警告には数えますが、完了の未読の印と完了の通知は、子の分を別には出しません。内部の guardian・review・compaction のスレッドは、今までどおり除きます。
- 協調の item の `agentsStates` で、届かなかった子の完了を補えます。ツール自身の状態は、子の状態ではありません。spawn が完了しても、wait が時間切れになっても、相手の子は動いていることがあります。ツールが始まったときに捉えた相手のターンの ID で、子の新しいターンを古い wait の結果から守ります。相手が動いているというスナップショットで、待っている承認が消えたり、完了した子が生き返ったりはしません。遅れて来た、スレッドが動いているという状態でも、`turn/started` なしに、終わったターンが生き返ることはありません。しばらく動きがないことや、プロンプトの文字の照らし合わせで、ターンが終わったと推し量ることはしません。
- 題名と説明を作るための内部のスレッドは、`threadSource`（`thread_title` か `thread_description`）で除きます。クライアントの start・fork の依頼に付いた source も見ます。知らないスレッドの通知は、待っている start・fork の応答を待つので、内部のスレッドの行が一瞬できることはありません。除いた ID は、閉じたあとも、遅れて来たイベントでも、除いたままです。これらのスレッドは、数、未読の結果、通知、止めるときの警告に関わりません。アカウントと利用枠を見ることは、これとは別に続けます。ユーザーが作った一時的なスレッドは、動いている間は出ますが、Worktabs の履歴には保存しません。
- `tabs.json` には、開いているタブごとに、Codex の移動のための情報を残します。プロバイダー、スレッドとターンの ID、題名、最後のプロンプト、cwd、Worktabs のアーカイブの印です。プロセスの ID、実行中の状態、未読の結果、認証のデータは残しません。会話の変化による書き込みはまとめ、終了するときに書き出します。戻した行は待機中です。クリックするか拡張が開くまで、別の app-server を起動したり、スレッドを再開したりしません。
- Codex の行をクリックすると、拡張を有効にし、workbench の opener で `<vscode.env.uriScheme>://openai.chatgpt/local/<thread-id>` を開きます。拡張の URI ハンドラーが、チャットのサイドバーにフォーカスを移し、そのスレッドに移ります。会話のエディタは作りません。プロバイダーは会話のもので、タブの既定のエージェントが違っても変わりません。補助拡張が登録する前のクリックは、登録するまで取っておきます。タブを切り替えると、その待っている移動は取り消します。送れなかったときや、`thread/resume` が断られたときは、はっきり警告を出し、Codex のサイドバーを開いてみます。
- Worktabs のアーカイブは、行を隠すだけです。`thread/archive` は出さず、保存された Codex のログには触れません。`thread/archived` と `thread/deleted` のイベントを見たら、保存した行を消します。`thread/closed` では、持っていたスレッドを手放すだけです。オブザーバーが自分から `thread/list`・`thread/resume`・`thread/fork` を依頼することはありません。

やりとりするイベントは、[OpenAI の公式の app-server のドキュメント](https://learn.chatgpt.com/docs/app-server)にあります。CLI の差し替えとサイドバーの URI ハンドラーは、拡張とつなぐところなので、拡張を更新したら両方を確かめます。

### Claude Code の hooks

- 会話ごとに、それを動かしている claude のプロセスを記録します。同じ claude が別の会話に移ると前の会話を外し、プロセスが終わる（パネルを閉じる）と会話も終わったとみなします。SessionEnd は来ないことが多く、同じ会話が 2 つのパネルで開いていることもあるためです。
- 拡張は、パネルを開くとすぐに claude を起動します（すぐに終わる claude を起動することもあります）。そのため、プロンプトを送った会話と、履歴から再開した会話だけを、会話の行にします。
- 会話の題名は transcript（JSONL）の `custom-title`（名前を変えたとき）か `ai-title` から読みます。
- 拡張は、パネルの中で別の会話に移っても、前の会話の claude を止めません（止めるのは、パネルを閉じたとき、再読み込みしたときなど）。このため、背後に回った会話も行に残ります。サイドバーでアーカイブした会話には印を付け、行にもタブのバッジにも出しません。印はメモリーにだけ持ち（行があるのは claude が動いている間だけなので）、作業中か承認待ちになると外します。拡張の会話一覧のアーカイブは、拡張の中（`globalState`）にあり、ほかの拡張からもアプリからも扱えないので、同期しません。
- 権限を「No」で断ったときや、再読み込みで中断したときは hook が出ません。このため transcript に残る中断の記録を監視して、状態を戻します。
- 会話ごとに、今の状態になった時刻を記録します（状態が変わったときだけ。同じ状態の hook では変えません）。サイドバーは、これと今の時刻から経過時間を出し、行を作り直さずに 10 秒ごとに文字だけを進めます。時間の書き方は `src/sidebar/time.js` にあり、ページとテストの両方から読みます。

## webview の互換性の確認

`src/conversations/webview-react.js` は、会話が見えているかの判定、Codex の承認、primary 以外の worktree の初回の案内で使う、公開されていない React の探り方を共有します。DOM のノードに付いた `__reactFiber$` をルートまでたどり、`stateNode.current` からそのノードそのものを探します。付いていたものの alternate の props を、今の状態として使うことはありません。外れたノード、ルートがない、マウントされていないノード、循環、たどる量の上限のときは、読めないという結果をはっきり返します。祖先をたどるのは、512 段と 10,000 ノードまでです。公式の Codex 拡張 26.1007.21434 では、最初の案内の見出しの祖先は 134、再開したスレッドの権限の操作の祖先は 257 あります。前の 100 段の上限では、これらの正しくマウントされた操作を退けていました。React の要素の props も量を区切ります。機能ごとの探り方は、それぞれの意味を表す ID、使えるかの確認、コールバック、代わりの扱いを持ちます。同じ関数を、Node に頼らずに、注入するスクリプトへ書き出します。

これらは拡張の内部の形で、公開された API ではありません。読むたびに今のツリーを探し直すので、履歴を切り替えたときや、ボタンが置き換わったときに、古い props を使い回すことはありません。知らない形のときは、未読の結果を残し、Codex の承認のモードはそのままにし、初回の案内の画面も使えるままにします。未読を消すのは、会話の ID がちょうど一致したときだけです。承認を見張る部分は、ユーザーが自分でした選択を守り、選んだものを次のスナップショットで確かめます。初回の案内は、今までどおり primary 以外の worktree だけで、案内（walkthrough）自身の完了のコールバックを呼びます。注入し直すと、前の見張りを片付けます。片付けた見張りは、遅れて来た非同期の結果を無視します。

## Codex の承認の初期設定

- Worktabs の設定の `codexApprovalMode` は、Claude の `permissionMode` とは別です。設定では `auto-review` か `manual` を保存します。既定は、使えるなら自動審査です。
- `openai.chatgpt` の webview のフレームが読み込まれると、`src/main.js` が `src/codex/codex-approval.js` のオブザーバーを入れます。オブザーバーは、翻訳されたラベルや拡張の版ではなく、React の権限の選択欄が描いた要素の props を読みます。古いコールバックの形と、プロファイルを選ぶ形は、拡張 26.1007.21434 で調べました。選択欄は、アカウントで使える機能、app-server の機能、設定、管理者が決めた要件を解決してから、選べる選択肢を出します。
- オブザーバーは、選べる選択肢だけを、拡張自身の守りの付いたコールバックで選びます。このコールバックは、覚えている選択と権限の上書きを一緒に更新します。Worktabs は、app-server の項目、審査役の列挙値、承認の答え、余分なユーザーのターンを送りません。`config.toml` に書かず、CLI のプロキシも変えず、ほかのアプリの拡張の保存領域にも触れません。
- 対象は、ローカルの拡張ホストにある、知っている形の空の入力欄だけです。すでにあるスレッド、リモートのホスト、Full Access、カスタムのプロファイルは、選んであるものをそのままにします。ユーザーが自分でマウスやキーボードを操作すると、最初の設定をやめます。選べたことは、効いたと知らせる前に、選択欄で確かめます。
- フレームのオブザーバーは、入力欄の移り変わりを追い、新しい入力欄ごとに 1 回だけ設定を当てます。設定を変えると、次の入力欄からその設定になります。読み込みのやり直しは 10 秒までです。選択肢がない、知らない選択欄、制限、選べなかったときは、その回をやめます。起動時に繰り返しやり直すことはしません。更新、戻したとき、code-server の再起動のあとは、新しいフレームが、有効な拡張を見直します。Windows・macOS・WSL のタブごとに別々です。
- 効いているモードの元は、今までどおり拡張の権限の操作です。webview の `worktabsCodexApproval.result` にある診断の状態で、読み込み中、選択肢がない・制限されている、知らない形の選択欄、ユーザーが選んだ、すでにある会話、選べなかった、を見分けます。認証の失敗を、自動審査に対応していないとは知らせません。

## 通知

裏のタブの Claude か Codex の会話が、承認待ちになったり、終わったり、失敗したりすると、Electron の `Notification` で OS の通知を出します。終わったターンと失敗したターンは、見るまで未読のままです。閉じる・休止・再起動・自動休止では、ほかの会話のエラーがタブのバッジに出ていても、作業中と承認待ちの会話をすべて確かめます。

未読は、タブ全体ではなく会話ごとのものです。`src/conversations/seen-conversations.js` は、エージェントと会話の ID がちょうど一致するものを照らし合わせます。タブがアクティブになったとき、ウィンドウにフォーカスが来たとき、フォーカスのあるタブに未読の結果がある間は 1.5 秒ごとに、メインプロセスが見えている webview のフレームを読みます。チャットのエディタも、パネルの中ですでに読み込んだ会話に切り替えたときも、これで分かります。隠れたまま残っているフレームで、未読が消えることはありません。タブやフォーカスが変わると、待っている読み込みは無効になります。知らない形のスナップショット、読めなかったとき、1 秒より長くかかった読み込みでは、未読の印を残します。

webview のスナップショットは、見えている入力欄の、マウントされた React のツリーを読みます。Claude の入力欄は、`sessionId`・`isLoading`・`loadFailed` を持つセッションを持っています。Codex の権限の操作は `conversationId` と `hostId` を持ち、ローカルのスレッドだけが一致します。これらは拡張の内部のことです。知らない形なら結果は未読のままで、最後に開いたスレッドの ID や再開の hook を、見えている証拠にはしません。会話の行から前に出せたときに消すのは、その会話の結果だけです。補助拡張は、パネルにフォーカスを移しただけかではなく、頼まれた Claude の会話を開いたかを知らせます。完了はどれも未読から始まり、新しいスナップショットで見えていれば消します。通知を出すかは、今までどおりタブとウィンドウが見えているかだけで決めます。

macOS では、題名と本文を渡すだけです。クリックは、通知を出したアプリが動いている間だけ、その `Notification` の `click` に届きます。起動し直したあとの通知には、どの会話かを持たせる方法がないので、何もしません。

Windows では、トースト（XML）を組み立てます。クリックは、次の 2 つの道でアプリに届きます。

- アプリが動いている間に、そのアプリが出した通知をクリックしたとき: Electron は Windows のイベント（`Activated`）で受け、通知を出した `Notification` のオブジェクトの `click` に渡します。ただし、どこからも参照されていないオブジェクトは GC で回収され、`click` のリスナーも消えます。Windows はトーストが消えたあとも通知センターに残すので、アプリは出した通知を、クリックされるまで持っておきます。持つのは直近の 20 件です。Windows の通知センターに残るのは、アプリごとに 20 件までです。
- 起動し直す前に出た通知をクリックしたとき: オブジェクトがないので、Windows は Electron の COM サーバーを呼び、`Notification.handleActivation` に届きます。アプリが終了していれば、Windows がアプリを起動します。
  - 届くのはトーストの `launch` の文字列だけです。Electron が組み立てるトーストには `launch` がないので、アプリがトーストの XML を組み立て、タブと会話の id を入れます（`src/conversations/notifications.js`）。
  - Electron は、通知を初めて使うときに COM サーバーを登録します。アプリを起動したクリックも受けられるように、起動してすぐに登録させます。`handleActivation` は、タブを戻してから登録します。それより前のクリックは Electron が持っていて、登録したときに届きます。
  - 起動し直したあとは、まだ会話がわからないので、タブに移るだけです。

## シェルの環境（macOS）

Finder・Dock・Launchpad から起動したアプリの PATH は、launchd のもの（`/usr/bin:/bin:/usr/sbin:/sbin`）だけです。Homebrew の `/opt/homebrew/bin` や `~/go/bin` など、シェルの起動ファイルが足すものが入らないので、ghq・gh・claude が見つかりません。ghq が見つからないと、リポジトリの一覧が空になります。

- VS Code と同じく、起動時にログインシェル（`$SHELL -i -l -c`）で環境変数を読み、アプリの環境に取り込みます（`src/shell-env.js`）。PATH はシェルのものを先にして、アプリにしかないフォルダを後ろに足します。
- 読むのはウィンドウを作るのと並行して行い、最初のコマンド（リポジトリの一覧）を動かす前に待ちます。シェルが 10 秒で答えないときは、アプリの環境のままにします。
- 端末から起動したとき（`npm start`）も同じように読みます。

## WSL（Windows）

WSL のフォルダは、アプリの中では `\\wsl.localhost\<ディストリ名>\...` のパスで持ちます（`\\wsl$\...` もこの形に直します）。git・ghq・gh・code-server は WSL の中で動かし、そこから返ってきた Linux のパスを、この形に直します。使い方は [wsl.md](wsl.md) にあります。

- Windows の git は、WSL の中のリポジトリを `detected dubious ownership` で読めません。WSL の中の git なら読めます。
- アプリは、ディストリごとに小さなエージェント（`src/wsl/wsl-agent.js`）を WSL の中で動かします。WSL の `~/.worktabs/bin` に書き込み、code-server の node で `wsl.exe` から起動します。アプリとは標準入出力で 1 行ずつの JSON でやりとりします。
  - コマンドを WSL の中で実行します。`wsl.exe` の起動には 1 回 0.3〜0.5 秒かかり、worktree の追加は git を 6 回呼ぶので、エージェントを通して速くします。ghq と gh は、ユーザーのシェルの環境変数（`$SHELL -i -l`）で実行します。`~/go/bin` などに入れた ghq も見つかります。
  - code-server をタブごとに起動し、止めるときはその下のプロセス（拡張ホスト、claude、ターミナル）ごと止めます。`taskkill` で `wsl.exe` を止めても、WSL の中のプロセスは残るためです。アプリが終わると（落ちても）エージェントの標準入力が閉じるので、エージェントは起動したものをすべて止めてから終わります。
  - hooks と補助拡張からの依頼を、WSL の `127.0.0.1` で受けて、アプリに渡します。WSL の既定の NAT ネットワークでは、WSL の中から Windows の `127.0.0.1` に届かないためです。逆向き（Windows から WSL の `127.0.0.1` の code-server と補助拡張）は、WSL の localhost の転送で届きます。
  - hooks を送った claude のプロセスを見張り、終わったらアプリに知らせます（会話の行を消すため）。Windows ではアプリが `claude-wrap.exe` のプロセスを見ますが、WSL の中のプロセスは見えないためです。
- claude のラッパーは、Linux 用の `claude-wrap`（`src/wsl/wsl-claude-wrap.sh`）です。`claude-wrap.exe` と同じく `--settings` で hooks を足し、自分のプロセス ID を `WORKTABS_PROC_ID` で渡します。自分を claude に置き換える（`exec`）ので、この ID は claude のものです。SessionStart は、エージェントの `hook` モードで転送します。
- hooks の transcript と作業フォルダは Linux のパスで来るので、`\\wsl.localhost\...` に直して読みます。
- code-server の Linux 版は、ターミナル用のコマンドを `code-server` という名前でしか持っていません。そのままだと `code` は PATH の後ろにある Windows の VS Code を起動するので、同じフォルダに `code` のシンボリックリンクを作ります。
- 拡張は、Windows のタブに入っているのと同じ版を入れます。WSL のタブがどれも動いていないときに、版が違えば入れ直します（入れ直すと古い版は消えるので、動いているタブがあるときは待ちます）。

## チャット欄のフォーカス

Claude Code のチャット欄は、自分にフォーカスが来ると、少し後に入力欄へフォーカスを移します。そのときに、まだ自分にフォーカスがあるかを確かめません。

- 右のパネルとエディタのタブにチャット欄があると、フォーカスが一方から他方へすぐに移ったとき（ほかのアプリやサイドバーから戻って、前と違う方のチャット欄をクリックしたときなど）に、両方が入力欄へのフォーカスを待つことになります。すると 2 つのチャット欄が 1 秒に数百回フォーカスを奪い合い、画面がちらついて操作できなくなります。ウィンドウからフォーカスが外れるまで続きます。
- そこでアプリは、チャット欄の画面（webview の中の枠）が読み込まれるたびに、スクリプトからのフォーカス（`focus()`）に決まりを足します。ページのほかの場所にフォーカスがある間は、フォーカスを持っていないチャット欄はフォーカスを取れません。
- クリックでのフォーカスの移動と、VS Code がチャット欄にフォーカスを渡す動き（`window.focus()`）は、そのままです。フォーカスを渡されたチャット欄は、今までどおり入力欄にフォーカスを移します。
- 別のチャット欄に入力している間は、承認の確認などが出ても、そのチャット欄にフォーカスが移りません。

## スロットリング

Chromium のバックグラウンドスロットリングを無効にしています。有効なままだと、隠れたタブや後ろにあるウィンドウで Claude パネルの webview が止まり、処理が数分止まります。

## 更新

`src/code-server/extension-index.js` は、ローカルと WSL の読み取りのために、有効な拡張の一覧を読み解きます。小文字の ID、元の識別子、版、宣言したターゲットと既定のターゲット、相対的な場所、場所が正しいかを出します。操作のたびに新しいスナップショットを読むので、更新や戻したあとに、使わなくなったフォルダから古い実行ファイルを選ぶことはありません。CLI の選択と言語パックは、拡張フォルダの外を指す場所を受け付けません。インポートは、今までどおり選んだフォルダとマニフェストを一覧と照らし合わせ、インポートの情報がおかしければエラーにします。WSL の版の照らし合わせと更新の確認は、一覧が読めなくても続けます。ローカルへのインストールでは、壊れた一覧をエラーとして知らせます。ギャラリーとインポートの互換性の決まりは、呼ぶ側に残します。

`src/code-server/extension-imports.js` は、デスクトップの拡張を探すこと、プラットフォームとエンジンの確認、丸ごとのスナップショット、SHA-256 の確認、ターゲットごとの入手元、トランザクションでのローカルへのインポートを扱います。画面の側が選ぶのは、中身の分からない候補の ID で、実行ファイルのパスではありません。管理のための IPC は、設定のダイアログの web contents からだけ受けます。インポートした ID は、Open VSX の更新から外します。Codex には、Open VSX に自動で切り替える道はありません。デスクトップからのインポートは、記録したローカルの入手元とだけ比べます。埋め込みのギャラリーへのアクセスは、既定で切っています。詳しくは [extensions.md](extensions.md) にあります。

アプリは code-server と拡張の内部の動き（`?folder=` の URL、クッキーでの認証、`languagepacks.json`、ラッパーを使ったときの拡張の動き）に頼っているので、版を固定しています。更新の操作は [usage.md](usage.md#code-server-と拡張の更新) にあります。

- code-server は GitHub のリリースのうち Windows 版があるもの、拡張は Open VSX の、いま入っている版と同じプラットフォーム（win32-x64 など）の最新版と比べます。拡張は、いまの code-server の VS Code で動く版だけを候補にします。
- リリースは、gh が github.com にサインインしていれば `gh api` で、そうでなければサインインせずに読みます。GitHub は、サインインしていないアドレスには 1 時間に 60 回までしか答えず、会社のネットワークでは 1 つのアドレスを皆で使うためです。1 つの入手元が失敗しても、ほかは止まりません。GitHub の上限に当たっても、Open VSX の更新は、エラーと上限が終わる時刻と一緒に出ます。
- 拡張フォルダは全タブで共有です。新しい版を入れると古い版に削除の印が付き、どれかの code-server が次に画面を返したときに消えます。作業中のタブが使っている版も消えてしまうので、更新は作業中のタブがなくなるまで待ちます。
- 拡張は、更新前から使っている code-server のコマンドで入れます。元に戻すときも同じです。
- WSL には、Linux 向けのインポートを別に持ちます。Claude は、Windows で固定した版ではなく、Linux 向けに公開された版を使います。アプリが管理するほかの拡張は、当てはまるものは今までどおり揃えます。用意したインポートは、対応する WSL が次に起動したときに入ります。トランザクションでのスナップショットの復元と、隠れて行う起動の確認は、今は WSL ではなくローカルだけで行います。

## 未保存の編集

VS Code Web の既定は `files.autoSave: afterDelay`（約 1 秒で自動保存）なので、編集が失われることはほぼありません。自動保存を切った場合に備えて、閉じる・休止・再起動・再読み込み・終了の前に未保存のエディタがないかを確かめます。あれば確認を出し、アイドル時の自動休止の対象からも外します。

## view の分離とパッケージ版のアプリ

view（タブ、サイドバー、ダイアログの画面）は、どれも `src/window/web-preferences.js` の `viewPreferences` で作ります。コンテキストの分離（context isolation）とサンドボックスはオン、Node の統合（Node integration）はオフです。どれも Electron の既定ですが、変更でどれかがオフになったらテストが失敗するように、はっきり書いています。タブはアプリが決められないページ（code-server）を出し、サイドバーとダイアログの画面は、プリロードが出したものを通してだけメインプロセスに届きます。

パッケージ版のアプリは、Electron の fuse のうち 2 つを切り替えます（`package.json` の `electronFuses`）。`NODE_OPTIONS` と `NODE_EXTRA_CA_CERTS` の環境変数と、`--inspect` の引数を無視するので、ほかのプログラムがこれらを通して、アプリのプロセスで自分のコードを動かすことはできません。RunAsNode の fuse はオンのままです。macOS では、claude のラッパー（`src/agents/mac-claude-wrap.js`）とログインシェルの環境の読み込み（`src/shell-env.js`）が、`ELECTRON_RUN_AS_NODE` でアプリ自身の実行ファイルを Node として動かすためです。fuse が効くのは `npm run pack` とそのあとのビルドだけで、`npm start` は Electron をそのまま動かします。
