# worktree の追加と削除

[English](../worktrees.md) | **日本語**

worktree は、サイドバーから追加・削除できます。`git worktree` や Orca など、アプリの外で作ったものも、そのまま一覧に出て開けます。

primary 以外の worktree（git の linked worktree）のタブでは、エージェントの最初の案内を飛ばします。Claude は `claudeCode.hideOnboarding` を使います。Codex は、案内（ウォークスルー）を終えたときの処理を呼んで、チャットに戻ります。一度終えた案内がまた出たときも同じです。primary は、自分の案内と Claude の設定のままです。primary 以外の worktree の中のフォルダでも同じで、先に primary を開かなくても効きます。パネルを開き直したときや、Worktabs を起動し直したときも、また効きます。

`claudeCode.hideOnboarding` はタブごとの設定で、同じリポジトリのほかのタブとは共有しません。Worktabs は、primary 以外の worktree のタブが起動するときに、これを `true` にします。認証と権限は、今までどおりエージェントのふだんの流れで行います。Codex で案内を飛ばせるのは、拡張の内部の案内を見分けられるときだけです。対応していない版では、元の画面のままです（[limitations.md](limitations.md#codex-拡張)）。

## 追加

リポジトリの行の「＋」か、右クリックの「worktree を追加…」で、追加のダイアログが出ます。欄は 2 つです。

- **issue・PR かやること**（空でも作れます）: GitHub の issue か PR（`#20`、`20`、issue や PR の URL）か、やることを文で書きます（例: `サイドバーの幅をドラッグで変えられるようにする`）。
  - issue なら、`gh issue view` で題名を読んで下に出します。閉じている issue なら「（閉じています）」と出ます。
  - PR なら、その PR のブランチを取り出す worktree を作ります（下記「[PR から作る](#pr-から作る)」）。
  - 番号だけのときは、issue か PR かを gh の答えで決めます。ほかのリポジトリの issue や PR では作りません。
  - gh は、リポジトリのある場所で動かします（WSL のリポジトリなら WSL の中の gh で、そこでのログインが要ります）。
  - リモートが GitHub でないリポジトリ（GitLab・Bitbucket・Gitea・社内の Git サーバー、リモートのないもの）では、欄の名前は「やること」だけになり、書いたものはすべてやることとして扱います。`#20` や issue の URL も、gh では読まず、そのままブランチ名を考える材料と、新しい会話の入力欄に使います。
    - 番号だけ（`#20`・`20`）では、ブランチ名を考えられません。欄の下にそう出て、「ブランチ名を考える」は押せません。ブランチ名を自分で入れれば作れます。
    - GitHub かどうかは、サイドバーが読んだリモートで決めます（[architecture.md](architecture.md#github-のボタン)）。
- **ブランチ名**: 入力中に、何をするかが下に出ます。

Enter で作成、Esc でやめます。

### ブランチ名を考える

上の欄の横の「ブランチ名を考える」を押すと、上の欄の issue かやることから、Claude（`claude -p`、Sonnet）がブランチ名を考えて、下の欄に入れます。入った名前は、直してから作れます。

- 上の欄を書いて、ブランチ名が空のまま Enter を押しても、名前を考えます。
- 時間は 5〜10 秒ほどです（claude の起動に約 3 秒）。考えている間に上の欄を書き換えると、考えた名前は使いません。
- 最近のブランチ名（ローカルとリモート、新しい順に 15 個）を見本として渡すので、`feat/issue66` のような、そのリポジトリの付け方に合わせます。issue なら番号を名前に入れます。
- claude は、リポジトリのある場所で動かします（WSL のリポジトリなら WSL の中の claude で、そこでのログインが要ります）。ツール、MCP サーバー、ユーザーの設定（hooks など）は使わず、会話も残しません（`--no-session-persistence`）。Claude の会話の一覧に、名前を考えた会話は出ません。
- 使用量は、ふだんの Claude と同じ枠から使います（1 回で約 1,000 トークン）。
- PR なら、Claude には聞かず、PR のブランチの名前を入れます（ボタンは「PR のブランチ名を入れる」になります）。

### PR から作る

人の PR をレビューしたり、手元で動かしたりするための worktree を、PR の番号か URL から作ります（`gh pr checkout` と同じ取り出し方です）。

- PR を `gh pr view` で読み、上の欄の下に、番号・題名・PR のブランチを出します（例: `PR #71 題名（ブランチ feat/x）`）。フォークのブランチは `alice:patch-1` のように、マージ済み・閉じた PR は「マージ済み」「閉じています」も出します。
- 上の欄で Enter を押すと（「PR のブランチ名を入れる」でも）、ブランチ名の欄に名前が入ります。もう一度 Enter で作ります。名前は直せます。
  - 同じリポジトリのブランチから出した PR は、そのブランチの名前（`feat/x`）です。
  - フォークから出した PR は、フォークの持ち主を前に付けます（`alice/patch-1`）。フォークの `main` や、ほかのフォークの同じ名前のブランチと区別するためです。フォークが消えていれば `pr-<番号>` です。
- 作る前に、PR のブランチを fetch します（入力中の説明に「fetch して」と出ます）。人のブランチは手元にないか、古いことが多いためです。
  - 同じリポジトリのオープンな PR: `origin/<ブランチ>` を fetch し、それを追うブランチを作ります（「リモートにだけあるブランチ」と同じです）。push すると PR に足せます。
  - フォークからの PR と、マージ済み・閉じた PR: GitHub が PR ごとに持つ `refs/pull/<番号>/head` を fetch して、新しいブランチを作ります。マージ済み・閉じた PR は、ブランチが消えていることがあるためです。PR に後から push されたものは、pull で取り込めます（`branch.<ブランチ名>.merge` を `refs/pull/<番号>/head` にします。`gh pr checkout` と同じです）。push 先はありません。
- 同じ名前のローカルブランチがあれば、fetch せずにそのまま取り出します（入力中の説明に「PR は fetch しません」と出ます）。新しいコミットは pull で取り込んでください。
- fetch するのは、`gh pr view` が読んだリポジトリのリモート（origin、なければ最初のリモート）です。

### 作ったあと

- タブを開いて、そのタブで選んでいるエージェントの新しい会話を出し、入力欄にフォーカスを移します（VS Code の起動を待つので、10 秒ほどかかります）。会話を先に始めてから worktree に移ると、会話のパネルが元のタブの VS Code に残るので、この順にしています。
- issue から作ると、そのブランチの git の設定に issue の番号と題名を書きます（`branch.<ブランチ名>.worktabs-issue` と `branch.<ブランチ名>.worktabs-issue-title`）。サイドバーの worktree の行に `#20` のように出て、押すと GitHub で issue を開きます。ブランチを消すと、この設定も消えます。
- PR から作ると、同じように PR の番号と題名を書きます（`branch.<ブランチ名>.worktabs-pull` と `branch.<ブランチ名>.worktabs-pull-title`）。worktree の行には、その PR が状態の色と CI の結果つきで出ます（[usage.md の「PR と CI」](usage.md#pr-と-ci)）。フォークからの PR や、PR と違う名前のブランチでも出ます。
- 上の欄を書いたときは、新しい会話の入力欄に、issue なら「GitHub の issue #20「題名」を実装して」を、PR なら「GitHub の PR #71「題名」をレビューして」を、やることならその文を入れておきます。送信はしないので、直してから送れます。
  - この会話は、右のチャット欄に開きます。Claude Code 拡張の設定 `claudeCode.preferredLocation` が `panel`（エディタのタブ）でも、右のチャット欄です。ワークスペースの設定（`.vscode/settings.json`）で `preferredLocation` を決めているときだけ、その場所に開きます。
  - Claude Code でも Codex でも、直せる下書きとして入れます。Worktabs がやることを自動で送ることはありません。確かめてから、自分で送ってください。
  - Codex への入力は、入れてある拡張のチャット欄の作りによります。Worktabs は、見えていて空の、ローカルの新しい会話の入力欄が出るのを少し待ちます。すでにあるスレッドや下書きには触りません。開くか入れるのに失敗すると、警告にやることを出し、「タスクをコピー」で新しい会話に貼り付けられるようにします。
  - Claude Code では、右のチャット欄が初めて出たときに作る空の会話が背後に残り、その claude が 1 つ多く動きます（[limitations.md](limitations.md#claude-code-拡張)）。
  - 上の欄が空なら、右のチャット欄を出します。

### 置き場所とブランチ

- 置き場所は、リポジトリの隣の `<リポジトリ名>-<ブランチ名>` です（ブランチ名の `/` は `-` にします。例: `worktabs` で `feat/x` なら `..\worktabs-feat-x`）。
- ブランチは、同じ名前のローカルブランチがあればそれを取り出し、リモートにだけあればそれを追うブランチを作ります。どちらにもなければ、既定のブランチから新しく作ります（入力中の説明に、`origin/main から新しいブランチを作ります` のように出ます）。PR から作るときは、上の「[PR から作る](#pr-から作る)」のとおりです。
  - 起点は、リモートの既定のブランチ（`origin/HEAD` が指す `origin/main` など）です。primary で別のブランチを取り出していても、そのブランチからは作りません。ローカルの `main` ではなく `origin/main` にするのは、primary が別のブランチにいると、ローカルの `main` は pull されず古いままのことが多いためです。
  - 作る前に fetch はしません。`origin/main` は、VS Code の自動の fetch や、ほかの worktree での pull で新しくなります。最新から作りたいときは、先に fetch してください。
  - 新しいブランチに上流は設定しません。VS Code の「ブランチの発行」で、同じ名前のリモートブランチに push します。
  - リモートがない、または `origin/HEAD` がない（`git init` のあとに `git remote add` したリポジトリなど）ときは、ローカルの `main`、`master` の順に探します。どちらもなければ、primary で取り出しているブランチから作ります。`origin/HEAD` は `git remote set-head origin --auto` で作れます。
  - remote は `origin`、なければ最初の remote を使います。
- ghq の下に作っても、ghq の一覧からはリポジトリとして数えず、元のリポジトリの下にだけ出します。

### gitignore されたファイルのコピー（`.worktreeinclude`）

リポジトリの直下に `.worktreeinclude` があれば、そこに書いた gitignore されたファイル（`.env` など）を、primary から新しい worktree にコピーします。書き方と規則は Claude Code の [`.worktreeinclude`](https://code.claude.com/docs/en/worktrees#copy-gitignored-files-into-worktrees) と同じなので、1 つのファイルが Claude Code の作る worktree にも効きます。

- 書き方は `.gitignore` と同じです。パターンに当たり、かつ gitignore されているファイルだけをコピーします。git で管理しているファイルはコピーしません。
- フォルダごと gitignore されている場所（`node_modules` など）の中は、パターンがそのフォルダの名前を含むときだけ探します（例: `**/.claude/skills/*.md` は `.claude/` の中を探し、`**/config.json` は探しません）。大きなフォルダはコピーに時間がかかるので、書かないでください。
- 途中のフォルダのどれかが、新しい worktree でシンボリックリンク（かジャンクション）になっているファイルは、コピーしません。そのリンクはブランチから来たもので、ブランチは人の PR のこともあり、ファイルを worktree の外や、git で管理しているフォルダに送ってしまうことがあるためです。
- 入力中の説明に、コピーするファイルの数が出ます。コピーできなかったファイルがあっても worktree はそのまま作り、何をコピーできなかったかを知らせます。

## 削除

worktree の右クリックの「worktree を削除…」か、開いていない worktree の行にマウスを乗せると出るゴミ箱のボタンで消します（primary には出ません）。

- ゴミ箱は、タブとして開いていない worktree の行にだけ出ます。開いている行の右端には × があり、並べると閉じるつもりで消しかねないためです。開いている worktree は、× で閉じてから消します。
  - ゴミ箱は行の右端、開いている行で × がある場所に出ます。× で閉じたら、続けて同じ場所を押して消せます。押しても確認が出るだけなので、× を続けて押しても、すぐには消えません。
  - ロックされた worktree と、削除中の worktree には出ません。
  - PR がマージ済みで、ブランチの先頭が PR の最後のコミットと同じ worktree（下記）は、マウスを乗せなくてもゴミ箱が出ます。終わった worktree を見つけやすくするためです。PR は行に出すものと同じで、gh を呼ぶ回数は増えません。
- 次のときは削除しません。先に片付けてください。
  - その worktree で Claude が作業中・承認待ち（ほかのタブの会話が移ってきている場合も含む）
  - 保存していないファイルがある
  - コミットしていない変更（新しいファイルを含む）がある
  - `git worktree lock` でロックされている
- 確認のダイアログで、ブランチも一緒に削除するかを選べます。ほかのブランチ・リモート・タグにないコミットがあるときは、その数を示し、ブランチの削除は既定でオフにします。
- 確認のダイアログには、ブランチの PR の状態も出します（「PR #12 はマージ済みです。」「PR #12 はまだマージしていません（オープン）。」「PR #12 はマージせずにクローズしています。」）。PR の選び方は worktree の行と同じで、PR から作った worktree はその PR です。
  - PR がマージ済みで、ブランチの先頭が PR の最後のコミット（`headRefOid`）と同じなら、ほかにないコミットがあっても、その数と「どれも PR #12 に残っています」を出し、ブランチの削除を既定でオンにします。ダイアログも警告にしません。squash マージやリベースのマージのあと、GitHub がリモートのブランチを消し、fetch でリモート追跡ブランチも消えると、ブランチのコミットはほかのどこにもなくなります。それでも、GitHub は PR のコミットを残している（`refs/pull/<番号>/head`）ので、`git fetch origin pull/12/head:feat/x` で戻せます。
  - マージのあとにコミットを足したなどで、先頭が PR の最後のコミットと違うときは、そう出したうえで、ほかにないコミットは今までどおりに扱います（警告し、ブランチの削除は既定でオフ）。
  - gh がない・サインインしていない・PR がない・既定のブランチ・5 秒たっても答えがないときは、PR の状態を出さずに確認します。確認を長く待たせないためです。PR は、ほかにないコミットを数えるのと並べて読みます。
- gitignore されたファイルのうち、primary の同じパスにないか、中身が違うものは、確認のダイアログに一覧で出します（20 個まで。多いときは「ほか N 個」）。worktree で書き換えた `.env` や `.claude/settings.local.json`、手で置いたメモなどです。git は変更として数えないので、黙って消えるためです。削除は止めません。
  - `.worktreeinclude` でコピーしたままのファイルは、primary と同じ中身なので出ません。
  - フォルダごと gitignore されているもの（`node_modules/`・`dist/` など）は、中を見ません。作り直せるものが多く、毎回出すとダイアログを読まなくなるためです。
- ほかにないコミットがあるとき（マージ済みの PR に残っているものは除く）と、一覧に出す gitignore されたファイルがあるときは、ダイアログを警告にし、Enter ではキャンセルになるようにします。
- ほかにないコミットがあるブランチを一緒に削除したときは（マージ済みの PR に残っているものは除く）、ブランチ名と先頭のコミットを Windows の通知で出します（例: `ブランチ feat/x（abc1234）を削除しました` `戻すには git branch feat/x abc1234`）。worktree を消すと、その worktree の HEAD の履歴（reflog）も消えるので、あとからコミットをたどれなくなるためです。通知センターに残るので、あとから見返せます。どこからもたどれなくなったコミットを git が片付ける（`git gc`）までは、これで戻せます。
- フォルダを手で消した worktree は、git の一覧に残るので（`git worktree list` で prunable と出る）、サイドバーにも出続けます。ゴミ箱か右クリックの「worktree を削除…」で、git に残っている記録を消せます。ほかにないコミットは、フォルダがなくても数えます。
  - フォルダはあるのに git が worktree と見なせないもの（`.git` ファイルを消したなど）は、削除の対象にしません。中のファイルを確かめられないまま消さないためです。
- 開いているタブは、閉じて code-server を止めてから消します。フォルダを使っているプログラムがあると、しばらく待ってからやり直します。それでも消せないときは、エクスプローラー（macOS では Finder）やターミナルを閉じてから、もう一度削除してください。
- 消した worktree のタブの VS Code の状態（開いていたファイルなど）も消し、そのタブのポートを忘れます（[architecture.md](architecture.md#code-server)）。
- 削除すると、同じリポジトリの primary を前に出します（開いていなければ開きます）。マージや次の worktree の追加など、そのリポジトリの作業はそこで続けるためです。
  - ゴミ箱・worktree の行の右クリック・タブの右クリックのどこから消しても、消した worktree のタブが開いていても閉じていても、同じリポジトリのほかの worktree のタブを開いていても、primary に移ります。
  - 移るのは、確認で「削除」を選んだときです。削除に失敗しても primary にいます。確認でキャンセルしたときと、削除できないとき（上記）は、タブを切り替えません。
  - × でタブを閉じただけのときは、隣のタブに移ります（primary には移りません）。
- worktree の中のジャンクションやシンボリックリンク（ほかの worktree の `node_modules` へのリンクなど）は、リンクだけを外します。`git worktree remove` は、Windows ではリンク先の中身まで消してしまうためです。
